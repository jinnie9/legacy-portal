# 4-4. 코드베이스 구조 파악

`legacy-portal` 현재 상태(baseline)의 패키지 구조와 각 컴포넌트의 책임을 정리한 문서.
리팩토링 전 "레거시가 무엇을 하는지"를 파악하는 용도이며, 여기 적힌 구조·스멜은 전부 **관찰된 사실**이다.

## 전체 구조

```
com.ktds.portal
├── PortalApplication      (진입점)
├── DataSourceConfig        (DB 자동 선택)
├── DataSeeder               (초기 데이터 4명)
├── approval/  Entity + Repository + Service + Controller
├── notice/    Entity + Repository + Service            ← Controller 없음
├── schedule/  Entity + Repository + Service            ← Controller 없음
├── user/      Entity + Repository + Controller          ← Service 없음
└── common/    FileAuditLogger, SmtpMailSender (공통 협력 객체)
```

- 도메인 폴더(`approval`/`notice`/`schedule`/`user`) 구조는 동일하지 않다 — 각 도메인이 실제로 필요한 만큼만 계층을 갖추고 있다(예: `notice`·`schedule`은 아직 REST API가 없고, `user`는 조회만 있어 Service 계층 자체가 없음).
- 테스트 코드는 **한 건도 없다** (`src/test`에는 `application.properties`만 존재). 특성화 테스트 작성이 리팩토링의 선행 작업이 되어야 한다.

## 도메인별 책임

### `approval` (결재) — 이 프로젝트의 핵심 학습 대상
| 파일 | 책임 |
|---|---|
| `Approval` | 결재 문서 엔티티. `status`(0 임시저장·1 상신·2 승인·3 반려·9 취소), `type`(1 지출·2 휴가·3 구매·4 기타), `priority`(1 낮음·2 보통·3 높음)를 모두 `int`로 보관. 모든 필드에 public setter(캡슐화 없음). |
| `ApprovalRepository` | `findByDrafterId` / `findByApproverId` 조회만 있는 순수 JPA 리포지토리. |
| `ApprovalService` | **God Class**. 결재 생성·상태 전이(상신/승인/반려/취소)·권한 판정·메일 발송·감사 로그·화면용 라벨 변환·금액 등급 계산을 전부 혼자 수행. 특히 `processApproval(id, userId, action, reason)` 하나가 action 코드(1/2/3/9)로 분기하는 100줄 이상의 중첩 if 블록. `SmtpMailSender`·`FileAuditLogger`를 생성자 주입 없이 직접 `new`. |
| `ApprovalController` | `/api/approvals` — `POST`(생성), `POST /{id}/process`(상신·승인·반려·취소 통합 처리), `GET /drafts/{userId}`, `GET /inbox/{userId}`. 요청 바디를 DTO 없이 `Map<String,Object>`로 받아 캐스팅. |

**결재 상태 전이 규칙** (모두 서비스 내부에 숫자로 하드코딩):
- 상신(1): 임시저장(0)일 때만 가능. 지출(type=1)이면서 100만원 이상이면 priority를 자동으로 3(높음)으로 상향.
- 승인/반려(2/3): 상신(1) 상태 + 본인이 결재자 + `role >= 2`(팀장 이상)일 때만. 조건 불충족 시 **조용히 무시**(예외 없음).
- 취소(9): 임시저장(0) 또는 상신(1) 상태 + 본인이 기안자일 때만.

### `notice` (공지)
| 파일 | 책임 |
|---|---|
| `Notice` | 공지 엔티티. `status`(0 임시·1 게시·9 내림), `category`(1 일반·2 긴급·3 인사)를 `int`로 보관. |
| `NoticeRepository` | 조회 메서드 없는 순수 JPA 리포지토리. |
| `NoticeService` | 공지 생성·게시(`publish`)·상태 라벨 변환 담당. `ApprovalService`와 감사 로그·메일 발송·권한 판정(`role>=2`) 로직이 거의 동일하게 중복돼 있음. 게시 시 긴급(category=2) 공지면 전체 사용자에게 메일 발송. |
| (Controller 없음) | 아직 REST API로 노출되지 않음 — 서비스 계층만 존재. |

### `schedule` (일정)
| 파일 | 책임 |
|---|---|
| `Schedule` | 일정 엔티티. `status`(0 예정·1 확정·9 취소)를 `int`로 보관. |
| `ScheduleRepository` | `findByOwnerId` 조회 메서드 보유. |
| `ScheduleService` | 일정 생성(제목/시간 검증 + 동일 소유자 시간 겹침 검사 + 저장 + 감사 로그를 한 메서드에서 처리)·확정(`confirm`) 담당. 겹침 검사는 `flag1`이라는 불리언 변수로 직접 루프를 돌며 계산. 검증 실패 시 `null` 반환(원인 불명). |
| (Controller 없음) | 아직 REST API로 노출되지 않음. |

### `user` (사용자)
| 파일 | 책임 |
|---|---|
| `User` | 사용자 엔티티. `role`(1 사원·2 팀장·3 임원)을 `int`로 보관 — 결재/공지 서비스의 권한 판정(`role>=2`)이 이 값에 의존. |
| `UserRepository` | `JpaRepository` 그대로 사용. |
| `UserController` | `/api/users` — `GET`(전체 목록). 데모 프론트엔드의 "로그인(사용자 선택)" 화면용. Service 계층 없이 Controller가 Repository를 직접 호출. |

### `common` (공통 협력 객체)
| 파일 | 책임 |
|---|---|
| `FileAuditLogger` | 감사 로그 기록. 실제로는 콘솔 출력(`System.out.println`)만 수행 — 파일 저장은 아직 구현되지 않음. 인터페이스 없이 구체 클래스로 존재해 각 서비스가 직접 `new`. |
| `SmtpMailSender` | 메일 발송. 실제 SMTP 연동 없이 콘솔 출력만 수행. 마찬가지로 인터페이스 없이 각 서비스가 직접 `new`. |

### 애플리케이션 부트스트랩
| 파일 | 책임 |
|---|---|
| `PortalApplication` | `@SpringBootApplication` 표준 진입점. |
| `DataSourceConfig` | 시작 시 `localhost:3306/portal` MariaDB 연결을 2초 타임아웃으로 시도해보고, 실패하면 H2 인메모리(`jdbc:h2:mem:portal`)로 자동 폴백. 수강생이 별도 DB 설치 없이 바로 실행 가능하게 하는 장치. |
| `DataSeeder` | `CommandLineRunner`로 앱 시작 시 사용자 4명(김사원/박팀장/이임원/최사원, role 1/2/3/1)을 시딩. 이미 데이터가 있으면(`count() > 0`) 건너뜀. |

## 공통적으로 관찰되는 스멜 (도메인 간 반복)

- **매직넘버 상태값**: `status`/`type`/`category`/`priority`/`role`이 전부 `int`이며 의미는 주석에만 존재. 특히 `status` 값 체계가 도메인마다 다르다 — approval은 `9=취소`, notice/schedule도 `9=취소(내림)`이지만 각각 다른 상태 집합을 가짐.
- **중복된 감사 로그·메일 발송 로직**: `ApprovalService`·`NoticeService`가 거의 동일한 형식의 로그 문자열 생성과 메일 본문 조립 코드를 각자 갖고 있음.
- **권한 판정 중복**: `role >= 2`(팀장 이상) 체크가 `ApprovalService.processApproval`과 `NoticeService.publish`에 동일하게 반복.
- **직접 `new`로 인한 강결합**: `SmtpMailSender`, `FileAuditLogger` 모두 생성자 주입이 아니라 서비스 필드에서 직접 생성.
- **조용한 실패**: 권한 없음·상태 불일치·검증 실패 시 예외 없이 그냥 리턴(`return`) 또는 `null` 반환 — 호출자가 실패 원인을 알 수 없음. (CLAUDE.md 기준으로 이는 **리팩토링 단계에서 보존해야 하는 레거시 동작**.)
- **DTO 부재**: `ApprovalController`가 `Map<String, Object>`를 그대로 받아 캐스팅 — 잘못된 키/타입이 컴파일 타임이 아닌 런타임에 터짐.

## 아직 REST API로 노출되지 않은 영역

- `notice`, `schedule` 도메인은 Service까지만 구현되어 있고 Controller가 없다. 즉 현재 HTTP로 공지 작성/게시, 일정 생성/확정을 호출할 방법이 없다.
- `user` 도메인은 반대로 Service 없이 Controller가 Repository를 직접 호출하는 가장 단순한 구조다.
