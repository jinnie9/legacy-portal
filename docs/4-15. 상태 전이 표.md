# 4-15. 상태 전이 표

`ApprovalService.processApproval(id, userId, action, reason)`(75~160행)의 상태 전이 규칙을 action별로 정리한 문서.
이 표는 코드 사실을 그대로 옮긴 것이며, 리팩토링(예: docs/4-12 백로그 5번 God Class 분해) 전후로 동일하게 유지되어야 하는 **특성화 대상**이다.

## action별 전이 규칙

| action | 의미 | 선행 상태(status) 조건 | 추가 전제조건 | 결과 상태 | 부수 효과 | 조건 불충족 시 |
|---|---|---|---|---|---|---|
| `1` | 상신 (SUBMIT) | `status == 0`(임시저장) | 없음 | `status = 1`(상신). 추가로 `type==1`(지출) && `amount >= 1000000`이면 `priority`도 `3`(높음)으로 자동 상향 | 결재자에게 "[결재요청]" 메일 발송, 감사로그 `APPROVAL SUBMIT` | 아무 것도 안 함(조용히 무시) |
| `2` | 승인 (APPROVE) | `status == 1`(상신) | ① 요청자(`userId`)가 `approverId`와 일치 ② `user.role >= 2`(팀장 이상) | `status = 2`(승인) | 기안자에게 "[결재승인]" 메일 발송, 감사로그 `APPROVAL APPROVE` | 아무 것도 안 함(조용히 무시) |
| `3` | 반려 (REJECT) | `status == 1`(상신) | ① 요청자가 `approverId`와 일치 ② `user.role >= 2`(팀장 이상) | `status = 3`(반려), `rejectReason = reason`(검증 없이 그대로 저장, 빈 문자열도 통과) | 기안자에게 "[결재반려]" 메일 발송(사유 포함), 감사로그 `APPROVAL REJECT` | 아무 것도 안 함(조용히 무시) |
| `9` | 취소 (CANCEL) | `status == 0`(임시저장) **또는** `status == 1`(상신) | 요청자(`userId`)가 `drafterId`와 일치 | `status = 9`(취소) | 메일 발송 없음(다른 action과 다름), 감사로그 `APPROVAL CANCEL` | 아무 것도 안 함(조용히 무시) |

## 공통 선행 조건 (모든 action 공통, 76-84행)

- 대상 결재(`id`)가 존재해야 함 — 없으면 즉시 `return`(조용히 무시)
- 요청자(`userId`)가 `User` 테이블에 존재해야 함 — 없으면 즉시 `return`(조용히 무시)
- `action`이 1/2/3/9 중 하나가 아니면(예: 0, 4~8, 10 등) 어떤 `if`/`else if`에도 걸리지 않아 **아무 일도 일어나지 않음**

## 주목할 점

- 승인(2)과 반려(3)는 전제조건이 완전히 동일(상태 `1` + 본인 결재자 + `role>=2`)하며 결과 상태와 메일 문구, 즉 "일어나는 일"만 다르다 — docs/4-5(중복 코드 탐지)에서 짚은 부분과 그대로 대응한다.
- 취소(9)만 유일하게 시작 상태가 두 가지(`0` 또는 `1`) 허용되고, 유일하게 메일을 보내지 않는다.
- 네 가지 action 모두 조건 불충족 시 결과가 동일하게 "조용한 무시"다 — CLAUDE.md 기준 리팩토링 시 절대 바꾸면 안 되는 보존 대상(docs/smells.md 참고). 실제 화면 조작으로도 이 동작을 재현·검증했다(docs/4-14 사용자 테스트 보고서, 시나리오 5).
