## 2. processApproval() 상태 전이 규칙 (action별)

`ApprovalService.processApproval(id, userId, action, reason)` (75~160행) 기준.

| action | 의미 | 선행 상태(status) 조건 | 추가 전제조건 | 결과 상태 | 부수 효과 | 조건 불충족 시 |
|---|---|---|---|---|---|---|
| `1` | 상신 (SUBMIT) | `status == 0`(임시저장) | 없음 | `status = 1`(상신). `type==1`(지출) && `amount >= 1000000`이면 `priority`도 `3`(높음)으로 자동 상향 | 결재자에게 "[결재요청]" 메일, 감사로그 `APPROVAL SUBMIT` | 조용히 무시 |
| `2` | 승인 (APPROVE) | `status == 1`(상신) | ① 요청자 == `approverId` ② `role >= 2` | `status = 2`(승인) | 기안자에게 "[결재승인]" 메일, 감사로그 `APPROVAL APPROVE` | 조용히 무시 |
| `3` | 반려 (REJECT) | `status == 1`(상신) | ① 요청자 == `approverId` ② `role >= 2` | `status = 3`(반려), `rejectReason` 그대로 저장(검증 없음) | 기안자에게 "[결재반려]" 메일(사유 포함), 감사로그 `APPROVAL REJECT` | 조용히 무시 |
| `9` | 취소 (CANCEL) | `status == 0` 또는 `status == 1` | 요청자 == `drafterId` | `status = 9`(취소) | 메일 없음, 감사로그 `APPROVAL CANCEL` | 조용히 무시 |

**공통 선행 조건**: 대상 결재(`id`)와 요청자(`userId`)가 모두 존재해야 하며, 둘 중 하나라도 없으면 즉시 `return`(조용히 무시). `action`이 1/2/3/9가 아니면 어떤 분기에도 걸리지 않아 아무 일도 일어나지 않는다.

## 3. 테스트 ↔ 규칙 매핑

| 테스트 # | 검증하는 규칙 |
|---|---|
| 1 | action=1(상신)의 정상 전이 + 금액 임계값에 따른 `priority` 자동 상향, action=2(승인)의 정상 전이 |
| 2 | action=3(반려)의 정상 전이 + `rejectReason` 저장 |
| 3 | action=9(취소)가 `status==0`에서도 허용됨 |
| 4 | action=2(승인)의 "추가 전제조건 ②" 불충족 시 조용한 무시 |
| 5 | 공통 선행 조건("대상 결재 존재") 불충족 시 조용한 무시 |
| 6 | action=2(승인)의 "선행 상태 조건"(`status==1`) 불충족 시 조용한 무시 — 승인(2)에서는 재실행돼도 재전이되지 않음 |

표의 8개 셀(각 action의 선행조건·추가전제·결과·불충족시) 중 테스트가 직접 실행 경로로 확인한 것은 위 매핑대로다. 유일하게 자동 테스트로 커버하지 않은 것은 **반려(3)의 조건 불충족 케이스**와 **취소(9)의 조건 불충족 케이스**(권한 없는 사용자의 취소 시도 등)이며, 필요 시 7·8번 테스트로 확장할 수 있다.
