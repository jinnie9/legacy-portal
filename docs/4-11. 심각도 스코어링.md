# 4-11. 심각도 스코어링

`4-10`에서 정성적으로 매긴 심각도 순위를, **영향도 × 수정난이도** 정량 점수로 다시 채점한 문서.

## 채점 기준

- **영향도 (1~5)**: 이 스멜을 방치했을 때의 파급 효과 — 버그 위험, 다른 스멜의 근본 원인이 되는 정도, 코드베이스 전반에 퍼진 범위.
- **수정난이도 (1~5)**: 지금 당장 고치는 데 드는 부담 — 영향 범위의 넓이, 책임이 뒤섞여 있어 경계를 잘못 그을 위험, 테스트 없이 손댈 때의 회귀 가능성.
- **점수 = 영향도 × 수정난이도** (최대 25)
- **심각도(★) 변환**: 1~5점 ★ / 6~10점 ★★ / 11~15점 ★★★ / 16~20점 ★★★★ / 21~25점 ★★★★★

> **`4-10`과의 관계**: `4-10`의 순위는 "무엇을 먼저 처리해야 하는가"(선행 필요성) 기준이고, 이 문서의 점수는 "영향도와 난이도를 곱하면 얼마나 위험한 스멜인가"를 보는 별개의 정량 지표다. 두 문서의 순서가 완전히 같지 않을 수 있다 — 예를 들어 테스트 부재는 선행 조건으로서는 1순위지만, 이 스코어링에서는 God Class + Long Method가 더 높은 점수를 받는다(범위와 얽힘 정도가 더 크기 때문). **테스트 부재는 점수와 무관하게 항상 가장 먼저 처리한다.**

## 스코어링 표

| 스멜 | 영향도 | 수정난이도 | 점수 | 심각도 |
|---|---|---|---|---|
| **God Class + Long Method** (`ApprovalService.processApproval`) | 5 | 5 | 25 | ★★★★★ |
| **테스트 부재** | 5 | 4 | 20 | ★★★★ |
| **Primitive Obsession / 매직넘버** | 5 | 3 | 15 | ★★★ |
| **DTO 부재 + Long Parameter List** | 3 | 3 | 9 | ★★ |
| **중복 코드** | 4 | 2 | 8 | ★★ |
| **강결합 (직접 `new`)** | 3 | 2 | 6 | ★★ |
| **Feature Envy** | 3 | 2 | 6 | ★★ |
| **Poor Naming** | 2 | 1 | 2 | ★ |
| **Comment Smell** | 1 | 1 | 1 | ★ |

## 채점 근거

| 스멜 | 영향도 근거 | 수정난이도 근거 |
|---|---|---|
| God Class + Long Method | 검증·영속화·메일·로그·권한판정·포맷팅이 한 메서드(86줄·중첩 깊이 6)에 몰려 있어, 손대면 여러 책임이 동시에 흔들린다 — 파급력 최대. | 승인/반려 분기가 상태·본인확인·권한·null체크 4겹으로 얽혀 있어, 책임 경계를 잘못 나누면 조용한 실패 같은 기존 동작이 바뀔 위험이 가장 크다. |
| 테스트 부재 | 이게 없으면 나머지 8개 스멜을 고치는 모든 작업이 회귀 위험을 안고 진행된다 — 다른 스멜의 위험을 증폭시키는 승수 역할. | 4개 도메인 전체(특히 "조용한 무시" 같은 미묘한 동작)를 빠짐없이 관찰·기록해야 해서 범위가 넓다. 다만 새 로직을 만드는 게 아니라 현재 동작을 그대로 옮기는 작업이라 God Class 재구성보다는 상대적으로 덜 위험하다. |
| Primitive Obsession / 매직넘버 | 중복된 권한판정(`role>=2`)과 Feature Envy의 임계값 중복이 전부 여기서 비롯된다 — 다른 스멜의 근본 원인. | `@Convert`+`AttributeConverter` 패턴 자체는 기계적이지만, 도메인이 4개이고 `action`/`status` 값이 우연히 겹치는 지점처럼 설계 판단이 필요한 부분이 섞여 있다. |
| DTO 부재 + Long Parameter List | 오타·타입 오류가 컴파일이 아닌 런타임에야 드러나는 구조적 위험이 있지만, 지금 API 자체는 유효하게 동작 중이라 당장의 파급력은 중간 수준. | 기존 JSON 필드명·구조를 하나도 틀리지 않고 record로 옮겨야 해서 매핑 실수 여지가 있다. |
| 중복 코드 | 7개 패턴이 27곳 이상 퍼져 있고, 이미 `ScheduleService.confirm()`의 null-guard 누락처럼 불일치가 실제로 발생했다. | 위치가 이미 문서화(`4-5`)돼 있고 로직도 대부분 동일해, 공통 헬퍼로 추출하는 비교적 기계적인 작업이다. |
| 강결합 (직접 `new`) | 테스트 격리와 협력 객체 교체를 막지만, 대상이 콘솔 출력만 하는 단순 클래스 2개뿐이라 실질 파급력은 중간. | 인터페이스 추출 + 생성자 주입은 5곳만 고치면 되는 정형적인 작업. |
| Feature Envy | 도메인 규칙이 서비스에 있어 응집도가 떨어지지만, 지금 당장 버그를 유발하지는 않는다. | 계산 로직을 엔티티로 옮기는 것 자체는 간단하나, 중복된 임계값(100만원)을 하나로 통합하는 결정이 필요하다. |
| Poor Naming | 가독성 문제이며 동작에는 영향이 없다. | 이름 변경은 IDE 리네임 수준의 기계적 작업 — 테스트만 있으면 가장 안전하게 처리 가능. |
| Comment Smell | Poor Naming의 부산물일 뿐, 독립적인 파급력이 없다. | 이름을 고치면 저절로 해소되어 별도 작업이 필요 없다. |

## 참고 — 채점 대상에서 제외

`4-10`에서 이미 "스멜이 아니거나 손대면 안 되는 것"으로 분류한 아래 두 항목은 고칠 대상이 아니므로 영향도·난이도 채점 자체가 성립하지 않는다.

- **조용한 실패**(권한 없음·상태 불일치 시 예외 없이 무시) — 리팩토링 단계에서 동작 변경 금지(보존 대상).
- **구조적 비일관성**(notice/schedule Controller 없음, user Service 없음) — 미완성 기능이지 스멜이 아님.
