# 4-5. 중복 코드 탐지

`ApprovalService` · `NoticeService` · `ScheduleService` 세 서비스에서 관찰되는 중복 코드를 유형별로 정리한 문서.
아직 리팩토링은 하지 않았다 — CLAUDE.md 기준대로 **먼저 특성화 테스트로 현재 동작을 고정한 뒤**, 이 문서를 근거로 공통 모듈 추출 등을 진행해야 한다.

## 요약

| # | 중복 유형 | 등장 위치(파일:라인) | 발생 횟수 |
|---|---|---|---|
| 1 | 감사 로그 타임스탬프 포맷팅 + `audit.write` | Approval 62-65, 164-165 / Notice 44-45, 69-70 / Schedule 62-63, 76-77 | 6곳 |
| 2 | 메일 본문 조립("안녕하세요 …님,") + `mail.send` | Approval 101-107, 119-124, 138-144 / Notice 63-67 | 4곳 |
| 3 | 엔티티·사용자 조회 후 없으면 조용히 `return` | Approval 76-84 / Notice 50-53 / Schedule 68-71 | 3곳 |
| 4 | 권한 판정 `role >= 2` | Approval 114, 133 / Notice 56 | 3곳 |
| 5 | 상태값(int) → 한글 라벨 if-else 체인 | Approval 169-179 / Notice 76-82 | 2곳(+ Schedule은 아예 없음) |
| 6 | 본인 확인(`getXxxId().equals(userId)`) | Approval 113, 132, 152 / Schedule 72 | 4곳 |
| 7 | `setUpdatedAt(LocalDateTime.now())` 갱신 | Approval 58, 98, 116, 136, 154 (서비스 내부 중복) | 5곳 |

---

## 1. 감사 로그 타임스탬프 포맷팅 + `audit.write`

가장 넓게 퍼진 중복. 세 서비스 전부 아래와 동일한 2줄을 메시지 문자열만 바꿔 반복한다.

```java
String now = LocalDateTime.now().format(DateTimeFormatter.ofPattern("yyyy-MM-dd HH:mm:ss"));
audit.write("[" + now + "] <액션 이름> id=" + <id> + " by=" + <userId>);
```

- `ApprovalService.create()` (62-65행) — `APPROVAL CREATE`
- `ApprovalService.writeAudit()` (164-165행) — `processApproval`의 상신/승인/반려/취소 4곳에서 호출되는 private 헬퍼. **단, `create()` 자신은 이 헬퍼를 쓰지 않고 또 인라인으로 복붙**(주석에도 "그나마 추출했지만 create() 안에는 또 복붙이 남아 있다"고 명시된 부분 — 부분적/불완전한 중복 제거 사례).
- `NoticeService.create()` (44-45행) — `NOTICE CREATE`
- `NoticeService.publish()` (69-70행) — `NOTICE PUBLISH`
- `ScheduleService.create()` (62-63행) — `SCHEDULE CREATE`
- `ScheduleService.confirm()` (76-77행) — `SCHEDULE CONFIRM`

**차이나는 부분**: 로그 메시지의 액션 이름(`"APPROVAL CREATE"` 등)과 뒤에 붙는 필드(`type=` 유무 등)뿐. 포맷 패턴·구조·`audit.write` 호출 방식은 완전히 동일하다.

## 2. 메일 본문 조립 + `mail.send`

수신자를 조회하고, `null`이 아니면 인사말로 시작하는 본문을 만들어 메일을 보내는 패턴이 반복된다.

```java
User <수신자> = userRepo.findById(<id>).orElse(null);
if (<수신자> != null) {
    String body = "안녕하세요 " + <수신자>.getName() + "님,\n" + "<메시지>";
    mail.send(<수신자>.getEmail(), "[<태그>] " + <title>, body);
}
```

- `ApprovalService.processApproval()` 상신 분기(101-107행) — 결재자에게 "[결재요청]"
- `ApprovalService.processApproval()` 승인 분기(119-124행) — 기안자에게 "[결재승인]"
- `ApprovalService.processApproval()` 반려 분기(138-144행) — 기안자에게 "[결재반려]" (반려 사유 포함)
- `NoticeService.publish()`(63-67행) — 전체 사용자 루프를 돌며 "[긴급공지]" (단건 조회가 아니라 `userRepo.findAll()` 순회라는 점만 다르고 본문 조립 방식은 동일)

**차이나는 부분**: 인사말 뒤에 붙는 안내 문구, 메일 제목 태그, 수신자를 한 명 조회하는지 전체를 순회하는지. 본문 조립 문자열 결합 방식과 `mail.send` 호출부 구조는 동일하다.

## 3. 엔티티·사용자 조회 후 없으면 조용히 `return`

세 서비스의 상태 변경 메서드(`processApproval`/`publish`/`confirm`) 모두 동일한 순서로 시작한다.

```java
<Entity> x = repo.findById(id).orElse(null);
if (x == null) return;
User u = userRepo.findById(userId).orElse(null);
if (u == null) return;
```

- `ApprovalService.processApproval()` 76-84행
- `NoticeService.publish()` 50-53행
- `ScheduleService.confirm()` 68-71행

**차이나는 부분**: 없음(변수명 제외 완전 동일 구조). 세 곳 모두 대상이 없거나 사용자가 없으면 예외 없이 조용히 종료 — CLAUDE.md 기준 **동작 보존 대상**(리팩토링 시 이 "조용한 무시"를 예외로 바꾸면 동작 변경이 된다).

## 4. 권한 판정 `role >= 2`

"팀장 이상만 가능" 규칙이 두 서비스에 하드코딩되어 반복된다.

- `ApprovalService.processApproval()` 승인 분기 114행: `if (u.getRole() >= 2) {`
- `ApprovalService.processApproval()` 반려 분기 133행: `if (u.getRole() >= 2) {` (114행과 완전히 동일한 조건, 주석도 "위 승인 분기와 똑같은 판정 복붙"이라고 명시)
- `NoticeService.publish()` 56행: `if (u.getRole() >= 2) {` (주석도 "ApprovalService 와 똑같은 권한 판정 복붙"이라고 명시)

**차이나는 부분**: 없음. `role`의 의미(1=사원·2=팀장·3=임원)와 `>= 2` 임계값이 세 곳 모두 동일한 매직넘버로 하드코딩.

## 5. 상태값(int) → 한글 라벨 if-else 체인

같은 모양(`if (s == 값) return "라벨"` 체인, 마지막 `else`는 "알수없음")의 메서드가 두 서비스에 존재한다.

```java
// ApprovalService.statusLabel() 169-179행
if (s == 0) tmp = "임시저장";
else if (s == 1) tmp = "상신";
else if (s == 2) tmp = "승인";
else if (s == 3) tmp = "반려";
else if (s == 9) tmp = "취소";
else tmp = "알수없음";
```

```java
// NoticeService.statusLabel() 76-82행
if (s == 0) return "임시";
else if (s == 1) return "게시";
else if (s == 9) return "내림";
else return "알수없음";
```

**차이나는 부분**: 상태값 개수(Approval 5개 vs Notice 3개)와 라벨 문자열. 분기 구조·"알수없음" 기본값 처리 방식은 동일.
**비대칭 관찰**: `ScheduleService`에는 이 메서드 자체가 없다 — `status`(0 예정·1 확정·9 취소)를 라벨로 보여줄 방법이 아직 없다는 뜻이며, 나중에 이 패턴을 공통화할 때 Schedule 쪽 부재도 함께 고려해야 한다.

## 6. 본인 확인(actor-ID 비교) 패턴

"이 요청자가 해당 문서의 결재자/기안자/소유자 본인인가"를 확인하는 조건문이 반복된다.

- `ApprovalService.processApproval()` 승인 분기 113행: `if (d.getApproverId() != null && d.getApproverId().equals(userId)) {`
- `ApprovalService.processApproval()` 반려 분기 132행: `if (d.getApproverId() != null && d.getApproverId().equals(userId)) {` (113행과 동일)
- `ApprovalService.processApproval()` 취소 분기 152행: `if (d.getDrafterId() != null && d.getDrafterId().equals(userId)) {` (필드만 다름, 구조는 동일)
- `ScheduleService.confirm()` 72행: `if (sc.getOwnerId().equals(userId)) {` (구조는 같지만 **null 체크가 빠져 있음** — Approval 쪽과 미묘하게 다른 변형이라 NPE 가능성이 있는 지점)

**차이나는 부분**: 비교 대상 필드(`approverId`/`drafterId`/`ownerId`)와 null 가드 유무. "ID 필드 == userId면 본인"이라는 조건 자체의 형태는 동일.

## 7. `setUpdatedAt(LocalDateTime.now())` 갱신 (서비스 내부 중복)

다른 서비스와의 중복은 아니지만, `ApprovalService` 한 클래스 안에서 상태를 바꿀 때마다 동일한 한 줄이 반복된다: `create()`(58행), 상신(98행), 승인(116행), 반려(136행), 취소(154행). `Notice`/`Schedule` 엔티티에는 `updatedAt` 필드가 없어 이 중복은 Approval에 국한된다.

## 참고 — 중복 제거 시 유의할 점 (CLAUDE.md 불변 규칙)

- 위 패턴들을 공통 모듈로 추출하더라도 **로그 문자열 포맷·메일 제목/본문 문구·API 응답 구조는 글자 하나까지 그대로** 유지해야 한다(관찰 가능한 동작에 해당).
- 3번(조용한 `return`)과 6번(본인 확인 null 가드 유무 차이)은 **결함처럼 보여도 리팩토링 단계에서는 그대로 보존**한다. 예를 들어 `ScheduleService.confirm()`의 null 체크 누락을 추출 과정에서 "고쳐서" 넣으면 안 되고, 있는 그대로(Approval 쪽엔 있고 Schedule 쪽엔 없는 상태로) 옮겨야 한다.
- DB에는 계속 정수(status/role/type 등)를 그대로 저장해야 하므로, 공통화 시에도 `@Enumerated` 대신 `@Convert` + `AttributeConverter` 방식을 사용해야 한다.
