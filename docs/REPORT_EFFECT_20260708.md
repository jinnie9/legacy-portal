# REPORT_EFFECT — 리팩토링 효과 분석 (SonarQube 재분석 기반)

`docs/4-13`(리팩토링 착수 전, 커밋 `68b8033` 분석)과 지금(커밋 `7451ed0`, 리팩토링 완료 후) 시점에 **동일한 SonarQube 인스턴스로 재분석**해서 정량 비교한 문서. `docs/REPORT_20260708.md`(구조 변화 요약)와 달리, 이 문서는 "정적분석 지표가 실제로 얼마나 움직였는가"에 집중한다.

## 요약 — 무엇이 실제로 좋아졌는가

| 지표 | 리팩토링 전 (`68b8033`) | 리팩토링 후 (`7451ed0`) | 변화 |
|---|---|---|---|
| Cognitive Complexity | 100 | **71** | **-29 (-29%)** |
| Code Smells — 프로덕션 코드(`main`)만 | 37 | **28** | **-9 (-24%)** |
| 중복 라인 비율 | 1.4% | 1.1% | -0.3%p |
| Bugs | 0 | 0 | 변화 없음 |
| Vulnerabilities | 3 | 3 | 변화 없음(아래 참고) |
| Security Hotspots | 0 | 0 | 변화 없음 |
| ncloc | 633 | 718 | +85(+13%, 신규 enum/converter 클래스) |

**Cognitive Complexity 29% 감소**가 이번 리팩토링의 가장 뚜렷한 정량적 효과다 — `processApproval()`의 6단계 중첩을 guard clause + 메서드 추출로 평탄화한 결과가 SonarQube 지표에도 그대로 드러났다.

## "Code Smells 합계가 37→37, 안 줄어든 것처럼 보이는" 이유

SonarQube 대시보드에서 전체 Code Smells 합계만 보면 **37건 → 37건으로 동일해 보인다.** 그런데 이슈 목록을 파일별로 뜯어보면 이야기가 다르다.

| 구분 | 리팩토링 전 | 리팩토링 후 |
|---|---|---|
| `src/main` (프로덕션 코드) | 37건 | **28건** |
| `src/test` (특성화 테스트 파일) | 0건 (파일 자체가 없었음) | **9건** |
| 합계 | 37건 | 37건 |

`docs/4-13` 분석 시점엔 특성화 테스트 파일이 아직 없었다(그 분석은 커밋 `68b8033`, 테스트 파일은 그 뒤 `7742d08`에서 생성됨). 즉 **합계가 그대로인 건 우연의 일치**이고, 실제로는:
- 프로덕션 코드 스멜이 **37 → 28건(-9건, -24%)** 줄었고,
- 새로 생긴 9건은 전부 테스트 파일의 **한글 변수/필드명**(`기안자_사원_id` 등)을 SonarQube 기본 네이밍 규칙(`^[a-z][a-zA-Z0-9]*$`)이 인식하지 못해서 나온 것이다.

이 9건은 실제 결함이 아니라 **CLAUDE.md의 "메서드명은 한글 시나리오명으로" 요구사항과 SonarQube 기본 규칙이 충돌하는 지점**이다. 고치려면 테스트 네이밍 컨벤션 자체를 바꿔야 하는데, 그건 이 프로젝트가 의도적으로 선택한 방향(한글 시나리오명)을 되돌리는 것이므로 그대로 둔다 — 필요하면 SonarQube 쪽 Quality Profile에서 테스트 소스에 한해 이 규칙을 끄는 것이 정공법이다(이번 범위 밖).

## `case null` 빈 블록 이슈 — 발견하고 바로 고침

재분석 중 `switch`의 `case null -> { }`가 "빈 블록" 이슈로 새로 잡히는 것을 발견했다(주석이 중괄호 밖에 있어 SonarQube가 "설명이 없다"고 판단). 주석을 블록 안으로 옮겨 해소했다(커밋 `7451ed0`, 특성화 테스트 6개 green 유지 확인 후 커밋). 이 문서의 "리팩토링 후" 수치는 이 수정을 반영한 최종 상태 기준이다.

## 변화 없는 지표 — 불변 규칙이 지켜졌다는 증거

- **Bugs 0 → 0, Security Hotspots 0 → 0**: 리팩토링이 새로운 결함을 만들지 않았다.
- **Vulnerabilities 3 → 3**: 확인해보니 3건 전부 `DataSourceConfig.java`(MariaDB 하드코딩 비밀번호 관련)에 있고, 이번 리팩토링은 이 파일을 건드리지 않았다 — 그대로인 게 정상이다.
- **ncloc 증가(+85줄)**: `ApprovalStatus`/`ApprovalStatusConverter`/`ApprovalAction` 3개 신규 클래스와 상세 주석 때문. 코드 품질 개선이 항상 "줄 수 감소"로 나타나는 건 아니다 — 매직넘버 제거·이름 개선은 오히려 설명하는 코드(enum, 상수, 도메인 메서드)가 늘어나며 줄 수가 증가하는 경우가 많다.

## Coverage 관련 한계

`coverage` 지표는 리팩토링 전후 모두 **0.0%로 동일**하게 표시된다. 이건 "테스트가 없다"는 뜻이 아니라 — 특성화 테스트 6개가 실제로 존재하고 `ApprovalService`를 직접 호출해 검증하고 있다(`docs/4-16`, `docs/4-17` 참고) — **JaCoCo가 Maven 빌드에 연동되지 않아 SonarQube가 커버리지 데이터 자체를 못 받는 것**이다. 실제 커버리지 수치를 보려면 `jacoco-maven-plugin`을 `pom.xml`에 추가하고 `sonar.coverage.jacoco.xmlReportPaths`를 지정하는 별도 작업이 필요하다(이번 범위 밖, 후속 과제로 남김).
