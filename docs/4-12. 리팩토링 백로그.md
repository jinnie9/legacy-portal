# 4-12. 리팩토링 백로그

`docs/smells.md`(=`4-4`~`4-11` 종합)에 정리된 스멜을 실제로 처리할 순서대로 나열한 백로그.
순서는 `4-10`/`4-11`의 심각도 순위를 그대로 따르지 않는다 — **"어떤 게 제일 심각한가"가 아니라 "무엇을 먼저 처리해야 다음 작업이 안전해지는가"(의존관계)** 기준으로 재배열했다.

## 정렬 원칙

1. **테스트 없이는 아무것도 손대지 않는다** — 특성화 테스트가 항상 0순위.
2. **위험이 낮고 다른 작업의 기반이 되는 것부터** — 이름 개선·enum 전환처럼 그 자체로 안전하면서 이후 작업을 쉽게 만드는 항목을 앞에 둔다.
3. **근본 원인을 먼저** — 매직넘버(Primitive Obsession)는 중복 코드(권한판정)·Feature Envy(임계값)의 원인이므로 그 파생 스멜들보다 먼저 처리한다.
4. **가장 위험한 작업(God Class 분해)은 준비가 끝난 뒤에** — 이름·enum·중복 제거·DI가 먼저 정리되어야 `processApproval()` 분해가 상대적으로 안전해진다.
5. **API 계층 정리는 내부 구조가 안정된 마지막에** — DTO 도입은 내부가 계속 바뀌는 동안 먼저 해봐야 재작업만 늘어난다.

## 백로그에 포함하지 않은 항목

- **조용한 실패**(권한 없음·상태 불일치 시 예외 없이 무시) — CLAUDE.md 기준 리팩토링 단계에서 동작 변경 금지. 별도 재설계 단계의 논의 대상이라 이 백로그 범위 밖.
- **구조적 비일관성**(notice/schedule Controller 없음, user Service 없음) — 스멜이 아니라 미완성 기능. 신규 기능 개발 백로그에서 다룰 사안.

## 진행 방식 유의사항 (CLAUDE.md 불변 규칙)

각 항목을 완료할 때마다 0번에서 작성한 특성화 테스트가 **변경 없이 그대로 green**이어야 한다(호출·기대값·DB값 동일). 하나라도 깨지면 "리팩토링"이 아니라 "동작 변경"이 일어난 것이므로 즉시 되돌리고 원인을 확인한다.
