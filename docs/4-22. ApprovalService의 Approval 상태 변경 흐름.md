# 4-22. ApprovalService의 Approval 상태 변경 흐름

리팩토링(Rich Domain 전환) 이후 `ApprovalService`는 **더 이상 `status`를 직접 판단·변경하지 않는다.** 상태 전이·권한 판정은 `Approval` 도메인 메서드(`submit()`/`approve()`/`reject()`/`cancel()`)가 맡고, `ApprovalService`는 "호출 → 성공하면 저장·메일·감사로그"만 오케스트레이션한다.

## 예외 — 생성 시점의 직접 대입

`ApprovalService`가 `status` 필드를 직접 건드리는 곳은 **딱 한 곳, `create()`뿐**이다.

```java
public Approval create(...) {
    Approval approval = new Approval();
    ...
    approval.setStatus(ApprovalStatus.DRAFT);   // 최초 생성 시 초기값 설정 — 도메인 메서드가 아니라 setter
    ...
}
```

이건 "전이"가 아니라 "최초 상태 부여"라 도메인 메서드(전이 규칙)의 대상이 아니다. `Approval`이 여전히 모든 필드에 public setter를 열어두고 있다는 점(캡슐화 부재, 개선 대상으로 보존 중)과 맞물린 지점이기도 하다.

## processApproval() — action 코드별 위임 표

`processApproval(id, userId, action, reason)`은 공개 시그니처를 그대로 유지한 채, 내부에서 `ApprovalAction.fromCode(action)`으로 변환해 아래처럼 분기·위임한다.

| action(int) | ApprovalAction | ApprovalService private 메서드 | 위임 대상 Approval 도메인 메서드 | 전이 성공 조건 | 성공 시 |
|---|---|---|---|---|---|
| 1 | `SUBMIT` | `submit(approval, userId)` | `approval.submit()` | 현재 `status == DRAFT` | `DRAFT(0) → SUBMITTED(1)`. 부수효과: 지출(`type==1`)이고 100만원 이상이면 `priority`를 자동으로 3(높음)으로 상향 |
| 2 | `APPROVE` | `approve(approval, actor, userId)` | `approval.approve(actor, userId)` | `status == SUBMITTED` && `approverId.equals(userId)` && `actor.isManagerOrAbove()`(role≥2) | `SUBMITTED(1) → APPROVED(2)` |
| 3 | `REJECT` | `reject(approval, actor, userId, reason)` | `approval.reject(actor, userId, reason)` | 승인과 조건 동일(상태·본인·권한) | `SUBMITTED(1) → REJECTED(3)` + `rejectReason` 저장 |
| 9 | `CANCEL` | `cancel(approval, userId)` | `approval.cancel(userId)` | (`status == DRAFT` \|\| `status == SUBMITTED`) && `drafterId.equals(userId)` | `DRAFT/SUBMITTED → CANCELED(9)` |
| 그 외 정수 | `null`(`fromCode`가 null 반환) | 없음(`switch`의 `case null` 분기) | — | — | 상태 변화 없음 |

각 도메인 메서드는 **조건을 만족하지 못하면 아무것도 바꾸지 않고 `false`만 반환**한다. `ApprovalService`는 이 반환값을 보고:
- `true` → `repo.save(approval)` + (해당 시) `mail.send(...)` + `audit.write(...)`
- `false` → 즉시 `return` — 저장·메일·감사로그를 전부 건너뛴다(예외 없이 **조용히 무시**, 레거시 동작 보존)

## processApproval() 진입 전 가드 절

도메인 메서드를 호출하기도 전에 아래 두 조건에서 조용히 종료한다(둘 다 예외 없이 `return`):

```java
Approval approval = repo.findById(id).orElse(null);
if (approval == null) { return; }         // 존재하지 않는 결재 id
User actor = userRepo.findById(userId).orElse(null);
if (actor == null) { return; }            // 존재하지 않는 사용자
```

## 상태 전이 다이어그램

```
                 submit()                 approve()
   DRAFT(0) ─────────────────▶ SUBMITTED(1) ─────────────────▶ APPROVED(2)
      │                             │
      │ cancel()                    │ reject()          cancel()
      ▼                             ▼                       │
  CANCELED(9) ◀───────────────────────────────────────────────┘
                                REJECTED(3)
```

- `APPROVED`·`REJECTED`·`CANCELED`는 **종단 상태(terminal)** — 이후 어떤 action을 보내도 각 도메인 메서드의 상태 조건(`DRAFT`/`SUBMITTED`만 허용)에 걸려 항상 `false`를 반환하고 조용히 무시된다(예: 승인된 건을 다시 승인/반려/취소 시도해도 무반응 — 특성화 테스트 6번이 이 사실을 고정).

## 요약

- `ApprovalService`가 하는 일: **조회 → 도메인 메서드 호출 → 성공하면 저장/알림/기록, 실패하면 조용히 종료.**
- **상태를 "바꿀지 말지" 판단하는 주체는 `Approval` 자신**(Rich Domain) — 서비스에는 `status`를 비교하는 `if`가 하나도 없다(생성 시 초기값 대입 제외).
- "위반 시 예외 대신 `false`로 조용히 무시"하는 레거시 동작은 서비스의 가드 절과 도메인 메서드의 반환값 양쪽 모두에서 동일하게 보존된다.
