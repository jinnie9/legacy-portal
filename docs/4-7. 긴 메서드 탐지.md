# 4-7. 긴 메서드 탐지

전체 서비스/컨트롤러의 메서드를 줄 수(LOC)와 최대 중첩 깊이 기준으로 조사한 결과.
Getter/Setter, 인터페이스 선언(Repository), Entity 필드처럼 로직이 없는 코드는 표에서 제외했다.

**측정 기준**
- **줄 수**: 메서드 선언 줄부터 닫는 중괄호 줄까지(내부 주석·빈 줄 포함) 물리적 줄 수.
- **중첩 깊이**: 메서드 바디 자체를 1로 보고, `if`/`for`/`try`/`switch` 등 블록이 한 겹 감쌀 때마다 +1. `if – else if – else if` 처럼 나란히 이어지는 분기는 서로 중첩된 게 아니므로 깊이를 더하지 않는다(같은 깊이의 형제 블록).

## 결론

**50줄을 초과하는 메서드는 `ApprovalService.processApproval()` 단 하나(86줄)뿐이며, 이 프로젝트에서 가장 깊은 중첩(6단계)도 이 메서드에서 나온다.** CLAUDE.md에 이 클래스가 "이 과정의 주인공 안티패턴"이라고 명시된 이유가 정량적으로도 확인된다.

## `processApproval()` 중첩 깊이 상세 (86줄, 깊이 6)

action(1=상신·2=승인·3=반려·9=취소) 4개 분기 중 승인(2)·반려(3) 분기가 가장 깊다. 각 분기는 `if (proc == N) { if (상태 s) { if (본인 확인) { if (권한) { ... if (수신자 null 체크) { ... } } } } }` 형태로 겹겹이 쌓인다.

| 깊이 | 승인(action=2) 분기 조건 (113-127행) | 반려(action=3) 분기 조건 (132-146행) |
|---|---|---|
| 1 | 메서드 바디 | 메서드 바디 |
| 2 | `else if (proc == 2)` | `else if (proc == 3)` |
| 3 | `if (s == 1)` — 상신 상태일 때만 | `if (s == 1)` — 상신 상태일 때만 |
| 4 | `if (d.getApproverId() != null && ... equals(userId))` — 본인이 결재자인지 | `if (d.getApproverId() != null && ... equals(userId))` — 본인이 결재자인지 |
| 5 | `if (u.getRole() >= 2)` — 팀장 이상 권한 | `if (u.getRole() >= 2)` — 팀장 이상 권한 |
| 6 | `if (drafter != null)` — 메일 발송 대상 존재 확인 | `if (drafter != null)` — 메일 발송 대상 존재 확인 |

상신(action=1)·취소(action=9) 분기는 상대적으로 얕다(각각 최대 깊이 4). 이 두 분기와 승인/반려 분기 사이의 깊이 차이 자체가, "권한 판정 + 본인 확인 + null 체크"가 한 메서드 안에 뒤섞여 있다는 신호다(중복 코드 탐지 문서의 3·4·6번 패턴과 동일한 지점들이 여기서 깊이를 만들어낸다).

## 참고 — 두 번째로 깊은 지점

`NoticeService.publish()`(25줄, 깊이 5)가 그다음으로 깊다: `role>=2` → `status==0` → `category==2`(긴급) → `for (User member : ...)` 루프까지 4겹 들어간 뒤 메일을 보낸다. 50줄은 넘지 않지만, `processApproval()`과 동일한 "권한 판정 뒤에 조건부 메일 발송"이라는 모양을 그대로 반복하고 있어 함께 참고할 가치가 있다.
