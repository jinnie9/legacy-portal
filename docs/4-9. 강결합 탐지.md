# 4-9. 강결합 탐지

서비스가 협력 객체를 생성자 주입(DI) 없이 **직접 `new`로 생성**하는 지점을 정리한 문서. CLAUDE.md 리팩토링 방향 "직접 `new` → 생성자 주입(DIP)"의 대상 목록이다.

## 요약

| 서비스 | 필드 | 생성 위치 | 대상 클래스 |
|---|---|---|---|
| `ApprovalService` | `mail` | `ApprovalService.java:37` | `SmtpMailSender` |
| `ApprovalService` | `audit` | `ApprovalService.java:38` | `FileAuditLogger` |
| `NoticeService` | `mail` | `NoticeService.java:24` | `SmtpMailSender` |
| `NoticeService` | `audit` | `NoticeService.java:25` | `FileAuditLogger` |
| `ScheduleService` | `audit` | `ScheduleService.java:20` | `FileAuditLogger` |

**총 5곳**, 대상 클래스는 `SmtpMailSender`(2곳)·`FileAuditLogger`(3곳) 단 둘뿐이다. `ScheduleService`는 메일을 보내지 않으므로 `mail` 필드 자체가 없다 — 강결합 지점이 3곳으로 상대적으로 적은 이유다.

## 상세

```java
// ApprovalService.java 36-38행
// [스멜5] 강결합 — 협력 객체를 생성자 주입 없이 직접 new 한다. 테스트에서 갈아끼울 수 없다.
private final SmtpMailSender mail = new SmtpMailSender();
private final FileAuditLogger audit = new FileAuditLogger();
```

```java
// NoticeService.java 24-25행
private final SmtpMailSender mail = new SmtpMailSender();
private final FileAuditLogger audit = new FileAuditLogger();
```

```java
// ScheduleService.java 20행
private final FileAuditLogger audit = new FileAuditLogger();
```

세 서비스 모두 생성자에는 `Repository`만 주입받고(`ApprovalService(ApprovalRepository, UserRepository)` 등), `mail`/`audit`은 필드 초기화 시점에 직접 인스턴스화한다 — 즉 **같은 클래스 안에서 협력 객체별로 주입 방식이 다르다**(Repository는 DI, 공통 협력 객체는 직접 `new`).

## 왜 문제인가

- **인터페이스 부재**: `SmtpMailSender`·`FileAuditLogger` 모두 구현할 인터페이스가 없는 구체 클래스다(`common/SmtpMailSender.java`, `common/FileAuditLogger.java`). 설령 생성자 주입으로 바꾸더라도 타입을 구체 클래스로 받는다면 테스트 시 가짜 구현으로 교체할 수 없다 — 인터페이스 추출과 생성자 주입이 함께 필요하다.
- **테스트 불가능**: 현재 이 두 클래스는 각각 `System.out.println`으로 콘솔에 출력만 한다(실제 메일 전송·파일 저장 없음). 즉 지금 당장은 부작용이 "출력"뿐이라 테스트에 큰 지장은 없지만, 나중에 실제 SMTP·파일 I/O로 교체되는 순간 이 강결합 때문에 각 서비스 테스트가 실제 메일 발송/파일 쓰기를 매번 일으키게 된다.
- **협력 객체 교체 비용**: 로그 저장 방식을 파일→DB로 바꾸거나 메일 발송기를 다른 구현으로 바꾸려면, `new`로 직접 생성하는 3개 클래스(`ApprovalService`/`NoticeService`/`ScheduleService`) 전부를 찾아 고쳐야 한다.

## 참고 — 이 문서 범위에서 제외한 `new`

같은 코드베이스에 등장하는 아래 `new` 호출은 **DI 대상이 아니므로 이 문서에 포함하지 않았다** — 도메인 엔티티를 생성하는 정상적인 코드이지 협력 객체(서비스가 의존하는 외부 기능)를 생성하는 게 아니기 때문이다.

| 위치 | 코드 |
|---|---|
| `ApprovalService.java:48` | `Approval d = new Approval();` |
| `NoticeService.java:33` | `Notice n = new Notice();` |
| `ScheduleService.java:52` | `Schedule sc = new Schedule();` |
| `DataSeeder.java:24-27` | `new User(...)` × 4 (초기 데이터 시딩용) |

## 참고 — CLAUDE.md 개선 방향과의 연결

CLAUDE.md의 "직접 `new` → 생성자 주입(DIP)" 항목이 정확히 이 5곳을 가리킨다. 리팩토링 시:
- `SmtpMailSender`·`FileAuditLogger`에 인터페이스(예: `MailSender`, `AuditLogger`)를 추출하고,
- 세 서비스의 생성자에 해당 인터페이스 타입 파라미터를 추가해 Spring이 `@Component`/`@Service` 빈을 주입하도록 바꾼다.
- 단, **로그 문자열 포맷·메일 제목/본문 문구 등 관찰 가능한 동작은 그대로 유지**해야 한다(불변 규칙) — 이번 리팩토링은 어디까지나 "어떻게 만드는가"만 바꾸는 것이지 "무엇을 출력하는가"를 바꾸는 게 아니다.
