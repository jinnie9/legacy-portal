# 4-19. ApprovalService 책임 분석(SRP)

`ApprovalService.java`(리팩토링 후 최신 상태: enum 전환·processApproval 분해·계층 분리·DTO 도입 완료 시점)의 책임을 나열하고, "무엇이 바뀌면 이 코드가 바뀌는가"(SRP — 변경 이유) 기준으로 분류한 문서.

## 책임 목록 → SRP 축 분류

| # | SRP 축 (변경 이유) | 책임 내용 | 관련 코드 |
|---|---|---|---|
| C | **알림 채널/문구**가 바뀔 때 (이메일→슬랙 전환, 안내 문구 변경 등) | 상신·승인·반려 시 메일 본문 조립 + 발송 | `submit()`/`approvedBody()`/`rejectedBody()`, `mail.send(...)` 호출 |
| D | **감사 로그 형식/저장 방식**이 바뀔 때 | 각 처리 단계의 감사 로그 기록 | `writeAudit()`, 각 메서드의 `writeAudit(...)` 호출, `create()` 내부 인라인 로그 |
| E | **결재 생성 규칙**이 바뀔 때 (기본값, 필수 필드 등) | 새 결재 문서 초기화(`DRAFT` 상태로 저장) | `create()` |
| G | **조회 조건/방식**이 바뀔 때 | 기안함/결재함 목록 조회 | `myDrafts()`, `myInbox()` (Repository 단순 위임이라 영향은 작음) |

> ~~F. 화면 표시용 문구/등급 기준~~ — **제거됨.** `statusLabel()`/`amountGrade()`가 어디서도 호출되지 않는 미사용 메서드였음을 확인하고, Move Method로 각각 `ApprovalStatus.label()`/`AmountGrade.forAmount(long)`(신규 enum)로 완전히 옮기면서 서비스의 위임 래퍼까지 삭제했다(2026-07-09, docs/log.md 참고). 이 축은 더 이상 `ApprovalService`의 책임이 아니다.
>
> ~~A. 결재 워크플로우(상태 전이) 규칙~~ — **Approval로 이동.** `submit()`/`approve(User,Long)`/`reject(User,Long,String)`/`cancel(Long)`이 상태·본인확인·권한 판정을 직접 수행하고 `boolean`을 반환한다(위반 시 예외 대신 `false` — 조용한 무시 보존). `ApprovalService`의 동명 private 메서드는 이제 "호출 → 성공하면 저장·메일·감사로그"만 담당한다.
>
> ~~B. 금액 기반 우선순위 정책~~ — **Approval로 이동.** `EXPENSE_TYPE`/`HIGH_PRIORITY_AMOUNT_THRESHOLD`/`HIGH_PRIORITY` 상수와 함께 `submit()` 안으로 옮겨가 A축과 자연스럽게 합쳐졌다(같은 도메인 메서드가 소유).
>
> ~~H. 협력 객체 구성/인프라~~ — **해소.** `MailSender`/`AuditLogger` 인터페이스 + 생성자 주입으로 전환, `new SmtpMailSender()`/`new FileAuditLogger()` 제거.

## 결론

애초 8개였던 "변경 이유" 축 중 **F(표현 규칙)**, **A(워크플로우)**, **B(금액 정책)**, **H(협력 객체 구성)** — 4개가 서비스 밖으로 빠지면서 **4개(C/D/E/G)**만 남았다. 남은 축은 전부 "결재가 성공적으로 처리된 뒤 무엇을 하는가"(알림·기록·조회)에 관한 것들이라, 성격이 비교적 均질해졌다 — `docs/smells.md`의 God Class(1번 스멜)가 "메서드 단위로만 쪼갬, 책임 분산은 차후 과제"라고 남겨둔 문제의 상당 부분이 실제로 해소된 셈이다. 다만 C(알림)와 D(로그)가 여전히 각 메서드(submit/approve/reject)에 반복되는 형태로 남아 있어(docs/4-5 중복 코드), 다음으로는 이 둘을 하나의 "결재 처리 결과 통지" 개념으로 묶는 리팩토링을 고려해볼 만하다.
