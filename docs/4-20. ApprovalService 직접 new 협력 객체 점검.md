# 4-20. ApprovalService 직접 new 협력 객체 점검

`ApprovalService.java`에서 `new`로 직접 생성하는 대상을 전수 검색한 결과.

## 검색 결과

```
31: *                            new SmtpMailSender()/new FileAuditLogger() 직접 생성 제거.   ← 주석(과거 이력)
77:        Approval approval = new Approval();
```

`new`가 등장하는 자리는 파일 전체에 단 한 곳(77번째 줄)뿐이며, 그 대상은 **협력 객체(collaborator)가 아니라 이 메서드가 만들어 반환해야 하는 결과물(Entity)** 이다.

| 줄 | 코드 | 협력 객체인가? | 판단 근거 |
|---|---|---|---|
| 77 | `new Approval()` | 아니오 | `create()`가 생성해서 저장·반환하는 **대상 자체**(Approval 엔티티). 외부 서비스에 위임할 "협력자"가 아니라 이 메서드의 결과물이므로 DI 대상이 아니다 |
| 31 | `new SmtpMailSender()` / `new FileAuditLogger()` | (과거에는 예) | 현재 코드에는 없음 — 클래스 상단 Javadoc이 "직접 생성 제거"했다고 남긴 **이력 주석**일 뿐, 실제 호출부는 이미 삭제됨 |

## 결론 — 직접 new로 생성하는 협력 객체는 현재 0개

이전 리팩토링(발송 → `MailSender`, 기록 → `AuditLogger` 인터페이스 추출 + 생성자 주입, docs/log.md 참고)에서 `new SmtpMailSender()`/`new FileAuditLogger()`를 제거하면서, `ApprovalService`가 직접 `new`로 생성하던 협력 객체는 이미 모두 없어졌다. 현재 생성자로 주입받는 4개 협력 객체(`ApprovalRepository`, `UserRepository`, `MailSender`, `AuditLogger`)는 전부 생성자 파라미터로만 들어오고, 서비스 내부 어디에서도 `new`로 만들어지지 않는다.

```java
public ApprovalService(ApprovalRepository repo, UserRepository userRepo, MailSender mail, AuditLogger audit) {
    this.repo = repo;
    this.userRepo = userRepo;
    this.mail = mail;
    this.audit = audit;
}
```

즉 docs/4-9(강결합 탐지)에서 지적했던 "직접 new로 생성하는 협력 객체" 스멜은 **이 시점에 완전히 해소된 상태**이며, 추가로 걷어낼 대상이 남아 있지 않다.

> **후속(docs/log.md 참고)**: 이 문서 작성 직후 `SmtpMailSender`/`FileAuditLogger`가 실제 동작(콘솔 출력)과 맞지 않는 이름이라는 지적에 따라 `ConsoleMailSender`/`ConsoleAuditLogger`로 개명했고, 같은 김에 `NoticeService`/`ScheduleService`에 남아 있던 동일 스멜(협력 객체 직접 new)도 생성자 주입으로 전환했다. 위 코드 스니펫과 표의 클래스명은 이 문서를 쓴 시점 기준이다.

## 참고 — `new`이지만 협력 객체가 아닌 것

- `new Approval()`(77번 줄): 위 표에서 설명한 대로 메서드의 산출물이라 협력 객체 판정에서 제외.
- `DateTimeFormatter.ofPattern(...)`(91·206번 줄): `new`가 아니라 정적 팩토리 메서드 호출이며, 상태 없는 값 객체(포맷터)라 DI 대상으로 보지 않음.
