# 4-18. approval 패키지 구조

리팩토링(status/action enum 전환, processApproval 분해, 계층별 하위 패키지 분리, 요청/응답 DTO 도입)을 거친 현재 시점의 `com.ktds.portal.approval` 패키지 파일 구성과 각 클래스의 계층을 정리한 문서. 10개 파일로 구성되며, 계층별 하위 패키지(`controller`/`service`/`domain`/`repository`/`dto`)로 나뉘어 있다.

## 계층별 분류

| 계층 | 패키지 | 파일 | 역할 |
|---|---|---|---|
| **Presentation (Web)** | `approval.controller` | `ApprovalController.java` | `/api/approvals` REST 엔드포인트. `dto` 패키지의 record로 요청을 받고 응답한다(Map/Entity 직접 노출 제거) |
| **Presentation (DTO)** | `approval.dto` | `CreateApprovalRequest.java` | `POST /api/approvals` 요청 record. JSON 필드명은 레거시 Map 키와 동일 |
| **Presentation (DTO)** | `approval.dto` | `ProcessRequest.java` | `POST /api/approvals/{id}/process` 요청 record. `reason` 누락 시 빈 문자열로 정규화(레거시와 동일) |
| **Presentation (DTO)** | `approval.dto` | `ApprovalResponse.java` | 모든 응답에 쓰이는 record. `Approval.from()` 정적 팩토리로 변환, `status`는 정수로 노출(계약 보존) |
| **Application (Service)** | `approval.service` | `ApprovalService.java` | 결재 생성·상신·승인·반려·취소 오케스트레이션(조회 → Approval 도메인 메서드 호출 → 성공 시 저장·메일·감사로그). 상태·권한 판정 자체는 Approval로 이동(docs/4-12 백로그 5번) |
| **Domain (Entity, Rich)** | `approval.domain` | `Approval.java` | JPA `@Entity`. `submit()`/`approve(User,Long)`/`reject(User,Long,String)`/`cancel(Long)`이 상태 전이·권한 규칙을 직접 판단해 `boolean`을 반환한다(위반 시 예외 대신 `false` — 조용한 무시 보존). Anemic에서 부분적으로 Rich Domain으로 전환됨 |
| **Domain (Value/Enum)** | `approval.domain` | `ApprovalStatus.java` | 결재 **결과 상태** enum(`DRAFT/SUBMITTED/APPROVED/REJECTED/CANCELED`). 라벨(`label()`)도 직접 소유 |
| **Domain (Value/Enum)** | `approval.domain` | `ApprovalAction.java` | `processApproval`의 **요청 액션** enum(`SUBMIT/APPROVE/REJECT/CANCEL`). `ApprovalStatus`와 코드값이 우연히 겹치지만 개념이 달라 분리(docs/4-8 참고) |
| **Persistence (Infra)** | `approval.domain` | `ApprovalStatusConverter.java` | JPA `AttributeConverter<ApprovalStatus, Integer>`. `ApprovalStatus` ↔ DB 정수 매핑(DB 저장값 불변 규칙 준수). Entity와 밀접히 얽혀 있어 `domain` 패키지에 함께 둠 |
| **Persistence (Repository)** | `approval.repository` | `ApprovalRepository.java` | `JpaRepository<Approval, Long>` — `findByDrafterId`/`findByApproverId` 조회 메서드만 추가 |

패키지 구조:
```
com.ktds.portal.approval
├── controller/  ApprovalController
├── service/     ApprovalService
├── domain/      Approval, ApprovalStatus, ApprovalAction, ApprovalStatusConverter
├── repository/  ApprovalRepository
└── dto/         CreateApprovalRequest, ProcessRequest, ApprovalResponse
```

## 계층 흐름

```
[Web]        ApprovalController  ──uses──▶  dto.{CreateApprovalRequest, ProcessRequest, ApprovalResponse}
                    │  (title/content/type/priority/... 또는 id/userId/action/reason)
                    ▼
[Application] ApprovalService
                    │  ┌─ ApprovalAction.fromCode(action)  (요청 해석, 저장 안 됨)
                    │  └─ ApprovalStatus 비교·전이           (Approval의 필드)
                    ▼
[Domain]      Approval (Entity)  ──uses──▶  ApprovalStatus (enum)
                    │
                    ▼
[Persistence] ApprovalRepository  ──(status 필드 저장 시)──▶  ApprovalStatusConverter ──▶  DB(정수)
```

`ApprovalAction`은 DB에 저장되는 값이 아니라 **API 요청 파라미터(`action: int`)를 서비스 내부에서 해석하기 위한 값**이라 Persistence 계층에 컨버터가 없다 — `ApprovalStatus`(엔티티 필드, DB 저장 대상)와의 이 차이가 두 enum을 분리한 이유이기도 하다(docs/4-8, `ApprovalAction.java`의 클래스 주석 참고).

`ApprovalResponse`는 `Approval` 엔티티를 그대로 반환하지 않고 `from(Approval)` 정적 팩토리로 변환한다 — Service는 여전히 `Approval` 엔티티를 반환하고, **엔티티 비노출은 Presentation 경계(Controller)에서만** 이루어진다는 점에 유의(Service 계층까지 DTO를 쓰도록 바꾸지는 않았다).

## 참고 — common 패키지와의 관계 (Tight Coupling 해소)

`ApprovalService`는 더 이상 `ConsoleMailSender`/`ConsoleAuditLogger`(구 `SmtpMailSender`/`FileAuditLogger` — 실제 동작(콘솔 출력)과 일치하도록 개명, docs/log.md 참고)를 직접 `new` 하지 않는다. `com.ktds.portal.common`에 `MailSender`/`AuditLogger` 인터페이스를 추출하고, 두 클래스가 각각 구현 + `@Component` 등록되어 생성자 주입으로 연결된다. `approval` 패키지 밖(공통 인프라)이라 위 표에는 없지만, `ApprovalService`의 생성자 시그니처가 이 인터페이스에 의존한다. 같은 인터페이스로 `NoticeService`/`ScheduleService`도 강결합이 해소되었다(docs/4-9 강결합 탐지 참고).

## 참고 — 남은 Anemic한 부분

- 금액 등급(`AmountGrade`)·상태 라벨(`ApprovalStatus.label()`)은 도메인으로 옮겼고, 이번에 상태 전이·권한 판정도 옮겼지만, `Approval.type`/`priority` 필드는 아직 `int`다(enum 후보로 남음, docs/log.md의 "의도적으로 하지 않은 것" 참고 — `create()`가 외부 입력을 검증 없이 그대로 저장하는 레거시 동작과 충돌 위험 때문에 이번 범위에서 제외).
- 메일 본문 조립(`approvedBody`/`rejectedBody`)과 감사 로그 기록은 여전히 `ApprovalService`에 있다 — "무엇을 승인 가능한가"는 도메인으로, "승인되면 무엇을 하는가(알림·기록)"는 서비스에 남겨두는 경계를 의도적으로 유지했다.
