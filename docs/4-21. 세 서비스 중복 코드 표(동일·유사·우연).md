# 4-21. 세 서비스 중복 코드 표 (동일 · 유사 · 우연)

`ApprovalService`·`NoticeService`·`ScheduleService` 세 서비스(및 리팩토링으로 로직이 옮겨간 `Approval` 도메인)를 대상으로 중복 코드를 전수 조사하고, 성격에 따라 세 종류로 구분했다.

## 구분 기준

| 종류 | 정의 |
|---|---|
| **동일 중복** | 코드가 사실상 그대로 복사·붙여넣기된 수준 — 리터럴·타입·조건까지 거의 일치. **변경 이유가 하나**라서 한쪽이 바뀌면 다른 쪽도 반드시 같이 바뀌어야 한다. |
| **유사 중복** | 구조(패턴)와 의도는 같지만 타입·필드명·세부 조건이 다르다 — 공통 템플릿으로 추출은 가능하지만 글자 그대로 하나의 코드는 아니다. |
| **우연 중복** | 문법 구조(생김새)만 닮았을 뿐, 각기 **다른 도메인 규칙·다른 변경 이유**를 가진다. 합쳐서 추출하면 오히려 서로 다른 두 정책이 한 코드에 묶이는 실수가 된다. |

## 중복 코드 표

| # | 중복 코드 | 위치 | 종류 | 판단 근거 |
|---|---|---|---|---|
| 1 | 감사 로그 타임스탬프 생성 + `[시각] EVENT id=X by=Y` 문자열 조립 | ~~`ApprovalService.java:91,206` (`create()`, `writeAudit()`) · `NoticeService.java:46,71` (`create()`, `publish()`) · `ScheduleService.java:65,79` (`create()`, `confirm()`) — 총 6곳~~ | **동일 중복 → 해소됨** | `DateTimeFormatter.ofPattern("yyyy-MM-dd HH:mm:ss")` 리터럴이 6곳 모두 글자 하나 다르지 않고 동일하고, 뒤이은 `"[" + now + "] " + ... + " id=" + ... + " by=" + ...` 조립 형태도 동일했다. **Move Method로 해소**: `AuditLogger.write(String line)` → `write(action, id, userId)`로 시그니처를 좁히고, 타임스탬프 포맷팅·문자열 조립 자체를 `ConsoleAuditLogger`로 옮겼다(docs/log.md 참고). 세 서비스는 이제 `audit.write("EVENT", id, userId)`만 호출한다. |
| 2 | 대상 조회 → null이면 조용히 리턴 → 사용자 조회 → null이면 조용히 리턴 | `ApprovalService.java:106-114`(`processApproval`) · `NoticeService.java:52-55`(`publish`) · `ScheduleService.java:71-74`(`confirm`) | **유사 중복** | "먼저 대상 엔티티를 id로 찾고, 없으면 조용히 종료 → 그다음 행위자를 userId로 찾고, 없으면 조용히 종료"라는 **가드 절 구조가 3곳 모두 완전히 동일**하다. 다만 대상 타입(`Approval`/`Notice`/`Schedule`)이 서로 달라 하나의 제네릭 메서드로 추출하려면 별도 추상화가 필요하다 — 글자 그대로는 같지 않지만 구조는 하나의 이유(존재하지 않는 대상/행위자는 조용히 무시)로 묶여 있다. |
| 3 | 메일 알림 본문 템플릿("안녕하세요 {이름}님,\n{상태 설명}\n제목: {제목}") | `ApprovalService.java:145-147`(`submit`) · `169-171`(`approvedBody`) · `189-192`(`rejectedBody`) · `NoticeService.java:66-67`(`publish` 인라인) — **총 4곳** | **유사 중복** | 첫 줄 `"안녕하세요 " + 이름 + "님,\n"`과 마지막 `"제목: " + 제목` 골격은 4곳 모두 동일하지만, 가운데 상태 설명 문장(`"결재 요청이 도착했습니다"`/`"승인되었습니다"`/`"반려되었습니다"`/`"긴급 공지가 게시되었습니다"`)과 부가 정보(기안자ID, 반려 사유)는 케이스마다 다르다 — 공통 템플릿 메서드(예: 인사말+제목 조립을 맡고 본문을 매개변수로 받는 형태)로 추출할 여지가 있는 전형적 유사 중복. |
| 4 | 메일 제목 `"[카테고리] " + 제목` 규칙 | `ApprovalService.java:148,163,183`(`"[결재요청]"`/`"[결재승인]"`/`"[결재반려]"`) · `NoticeService.java:68`(`"[긴급공지]"`) | **유사 중복** | `"[" + 카테고리 + "] " + title` 형태의 제목 조립 규칙 자체는 4곳 모두 동일하나, 카테고리 문자열과 호출 시점(누구에게 보내는지)이 각기 다르다 — 위 3번 항목(본문)과 짝을 이루는 알림 규약이라 함께 추출 대상. |
| 5 | "팀장 이상" 권한 판정(`role >= 2`) | `Approval.approve()/reject()` → `User.isManagerOrAbove()`(이미 리팩토링됨, `role>=2`) 위임 vs `NoticeService.java:58` `if (u.getRole() >= 2)`(원시 그대로) | **동일 중복** | **완전히 같은 비즈니스 규칙**(role 2 이상 = 팀장 이상 권한)이 정수 리터럴 `2`까지 똑같이 두 곳에 존재한다 — 다만 한쪽(Approval 결재 승인/반려)은 이미 `User.isManagerOrAbove()`로 Move Method 되어 이름이 붙었고, 다른 쪽(NoticeService 공지 게시)은 아직 원시 `>= 2` 비교로 남아 있다. **"이미 추출된 공통 로직을 다른 한 곳이 아직 안 쓰고 있는" 가장 쉬운 dedup 대상.** |
| 6 | 상태값 매직넘버 분기(`getStatus() == 0` 류) | `NoticeService.java:59`(`status==0` → 임시) · `ScheduleService.java:45`(`status!=9` → 취소 제외) · `76`(`status==0` → 예정) | **우연 중복** | 셋 다 `if (x.getStatus() == 정수)` 라는 **같은 문법 모양**이지만, 같은 정수 `0`이 공지에서는 "임시(게시 전)", 일정에서는 "예정(확정 전)"으로 **완전히 다른 도메인 의미**를 가진다. 겉모습이 닮았다고 하나의 "상태 확인 유틸"로 합치면, 공지 정책 변경이 일정 정책에 실수로 영향을 주는 결합이 생긴다 — 합치면 안 되는 우연의 일치. |
| 7 | 소유자 본인 확인(`필드.equals(userId)`) | `Approval.cancel()`(`drafterId==null \|\| !drafterId.equals(userId)`) · `Approval.approve()/reject()`(`approverId==null \|\| !approverId.equals(userId)`) vs `ScheduleService.java:75`(`sc.getOwnerId().equals(userId)`, null 체크 없음) | **유사 중복** | "이 리소스가 나(userId)의 것인가"를 확인하는 **의도는 동일**하지만, `Approval` 쪽은 필드가 `null`일 가능성을 먼저 걸러내는 가드가 있고 `ScheduleService`는 없다(만약 `getOwnerId()`가 `null`이면 NPE 위험 — 완전히 동일한 코드는 아니라는 방증). 구조는 유사하되 견고성 디테일이 달라 유사 중복으로 분류. |
| 8 | 엔티티 생성 초기화(`new X(); setter...; repo.save(x);`) | `ApprovalService.create():77-88` · `NoticeService.create():35-43` · `ScheduleService.create():55-62` | **우연 중복** | "새 엔티티 만들고 필드 채우고 저장한다"는 뼈대는 셋 다 같아 보이지만, 채우는 필드 구성·개수·`createdAt`/`updatedAt` 유무가 전부 다르다(`Approval`은 둘 다 있음, `Notice`는 `createdAt`만, `Schedule`은 둘 다 없음). 이건 JPA 엔티티를 만들 때 **자연스럽게 비슷해 보이는 상용구**일 뿐, 하나로 추출하면 오히려 세 엔티티의 서로 무관한 필드 목록을 억지로 하나의 메서드에 우겨넣게 된다 — 추출 대상이 아닌 우연 중복의 전형. |
| 9 (참고) | 상태값 → 한글 라벨 if/else 사슬(`statusLabel`) | `NoticeService.java:78-84` | **해소된 항목(참고)** | 원래 `ApprovalService`에도 거의 동일한 5분기 `statusLabel()`이 있었으나, 이전 리팩토링(Move Method)으로 `ApprovalStatus.label()`(enum 필드)로 옮기며 완전히 제거되었다(docs/4-19 참고). 지금은 `NoticeService`에만 남아 있어 **"세 서비스 간 교차 중복"은 아니지만**, 같은 패턴을 이미 한 번 해소한 전례가 있다는 점에서 다음 dedup 후보로 남겨둔다. |

## 요약

- **동일 중복(1·5)**: 감사 로그 조립 로직, "팀장 이상" 권한 판정 — **가장 먼저 추출해야 할 대상**. 특히 5번은 이미 있는 `User.isManagerOrAbove()`를 `NoticeService`가 쓰기만 하면 되는 가장 저비용 dedup.
- **유사 중복(2·3·4·7)**: 조회 가드 절, 메일 본문/제목 템플릿, 본인 확인 — 공통 뼈대는 추출 가능하지만 타입·세부 조건 차이 때문에 다형성(제네릭/템플릿 메서드/추상화)이 필요한 대상.
- **우연 중복(6·8)**: 상태 매직넘버 분기, 엔티티 생성 상용구 — **추출하면 안 되는** 항목. 겉모습만 보고 합치면 서로 다른 도메인 정책이 뒤섞이는 위험이 있다(docs/4-5 "중복 코드 탐지"의 관점을 세 서비스 조합으로 재검증한 결과).
