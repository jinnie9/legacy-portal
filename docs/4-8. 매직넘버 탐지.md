# 4-8. 매직넘버 탐지

각 도메인 엔티티의 `int` 필드에 박혀 있는 매직넘버와, 서비스 코드 곳곳의 비교 연산에 등장하는 숫자 리터럴의 의미를 추정해 정리한 문서. CLAUDE.md 기준 "DB 저장값은 정수 그대로, 다만 enum + `@Convert`로 감싸서 의미를 드러내는" 리팩토링의 대상 목록이다.

## 요약 — 필드별 코드 체계

| 필드 | 위치 | 코드 → 의미 |
|---|---|---|
| `Approval.status` | `Approval.java:26` | 0=임시저장·1=상신·2=승인·3=반려·9=취소 |
| `Approval.type` | `Approval.java:25` | 1=지출·2=휴가·3=구매·4=기타 |
| `Approval.priority` | `Approval.java:27` | 1=낮음·2=보통·3=높음 |
| `Notice.status` | `Notice.java:19` | 0=임시·1=게시·9=내림 |
| `Notice.category` | `Notice.java:20` | 1=일반·2=긴급·3=인사 |
| `Schedule.status` | `Schedule.java:18` | 0=예정·1=확정·9=취소 |
| `User.role` | `User.java:19` | 1=사원·2=팀장·3=임원 |
| `ApprovalService.processApproval`의 `action` 파라미터 | `ApprovalService.java:73` (주석) | 1=상신·2=승인·3=반려·9=취소 |

세 개의 `status` 필드가 전부 `0/1/9`를 쓰지만(임시·확정 전 상태=0, 취소=9는 공통) 각 도메인마다 그 사이 값의 의미가 다르다 — 예를 들어 Approval만 2(승인)·3(반려)이 따로 있고, Notice·Schedule은 "게시/확정"만 있고 반려 개념이 없다. 세 필드가 같은 상수 집합을 공유하는 게 아니라 **도메인마다 독립적으로 우연히 겹치는 숫자**라는 점이 enum 설계 시 중요하다(하나의 공용 `Status` enum으로 묶으면 안 되고 도메인별 enum이 필요하다).

## 도메인별 상세

### Approval — `status` (0/1/2/3/9)

- `0` = 임시저장(DRAFT) — 생성 직후 초기값. `ApprovalService.create()` 53행: `d.setStatus(0);`
- `1` = 상신(SUBMITTED) — `processApproval()` 97행: `d.setStatus(1);` (action=1일 때 s==0 조건 통과 후)
- `2` = 승인(APPROVED) — 115행: `d.setStatus(2);`
- `3` = 반려(REJECTED) — 134행: `d.setStatus(3);`
- `9` = 취소(CANCELED) — 153행: `d.setStatus(9);` (왜 4~8을 건너뛰고 9인지 코드에 규칙이 없음 — 주석에도 "왜 9? 4~8은 비워둔 규칙 없는 번호"라고 명시)
- 라벨 변환 `statusLabel()`(169-179행)에서 0/1/2/3/9 다섯 값을 전부 하드코딩된 if-else로 문자열 매핑.

### Approval — `type` (1/2/3/4)

- `1`=지출, `2`=휴가, `3`=구매, `4`=기타. 정의는 `Approval.java:12` 주석에만 존재.
- 실제 분기: `processApproval()` 94행 `if (d.getType() == 1 && d.getAmount() >= 1000000)` — **지출(1)이면서 금액이 100만원 이상일 때만** priority 자동 상향. `type`의 나머지 값(2/3/4)에는 이 규칙이 적용되지 않는다는 게 숫자 `1` 하나에 암묵적으로 담겨 있다.

### Approval — `priority` (1/2/3)

- `1`=낮음, `2`=보통, `3`=높음. `ApprovalService.create()` 52행에서 `urgent` 플래그가 true면 `priority`를 무조건 `3`(높음)으로 덮어씀. 94-95행에서는 금액 조건으로도 `3`이 강제된다 — **"높음"에 도달하는 경로가 두 곳(요청의 urgent 플래그, 100만원 이상 지출)이라는 사실이 숫자 3 하나로만 표현**된다.

### Notice — `status` (0/1/9)

- `0`=임시, `1`=게시(PUBLISHED), `9`=내림. `NoticeService.create()` 37행에서 `0`으로 시작, `publish()` 58행에서 `1`로 전환. `9`(내림)로 바꾸는 코드는 현재 어디에도 없다 — **값은 정의돼 있지만 실제로 그 상태로 전이시키는 로직이 아직 구현되지 않은 상태**(4-4 문서에서 지적한 "Notice엔 Controller가 없다"는 사실과 함께, 내림 처리 자체가 미완성 기능일 가능성).

### Notice — `category` (1/2/3)

- `1`=일반, `2`=긴급, `3`=인사. 실제 분기는 `publish()` 62행 `if (n.getCategory() == 2)` 단 한 곳 — **긴급(2)일 때만 전 직원 메일 발송**. 1(일반)·3(인사)은 이 코드에서 구분되지 않고 동일하게 취급된다.

### Schedule — `status` (0/1/9)

- `0`=예정, `1`=확정(CONFIRMED), `9`=취소. `ScheduleService.create()` 58행에서 `0`으로 시작, `confirm()` 74행에서 `1`로 전환. 시간 겹침 검사(42행)에서 `s.getStatus() != 9`로 **취소된 일정은 겹침 계산에서 제외**한다는 규칙이 숫자 비교 하나로만 표현되어 있다. Notice와 마찬가지로 `9`(취소)로 전이시키는 코드는 없다.

### User — `role` (1/2/3)

- `1`=사원, `2`=팀장, `3`=임원. `DataSeeder`가 초기 사용자 4명을 role 1/2/3/1로 시딩(24-27행). 서비스 코드에서는 구체적인 값(1/2/3) 자체보다 **임계값 `role >= 2`("팀장 이상")** 형태로만 쓰인다 — `ApprovalService` 승인(114행)·반려(133행), `NoticeService.publish()`(56행) 총 3곳(중복 코드 탐지 문서의 4번 항목과 동일 지점).

### `action` 파라미터 — `processApproval(id, userId, action, reason)` (1/2/3/9)

- `ApprovalController`가 API 요청의 `"action"` 키를 그대로 `int`로 캐스팅해 전달(`ApprovalController.java:42`). 값의 의미는 상신=1·승인=2·반려=3·취소=9로 **Approval.status의 코드값과 우연히 동일**하다.
- 이 우연의 일치가 위험한 이유: `action=1`(상신 요청)이 들어오면 결과적으로 `status`도 `1`이 되고, `action=2`→`status=2`, `action=3`→`status=3`, `action=9`→`status=9`로 **입력 코드와 결과 코드가 매번 숫자까지 똑같다.** 코드만 보면 "왜 항상 같은 숫자인지"가 우연인지 설계인지 구분되지 않는다 — enum으로 분리할 때 `ApprovalAction`과 `ApprovalStatus`를 **일부러 같은 값으로 대응시킨 서로 다른 두 enum**으로 만들어야 하며, 하나의 enum으로 합치면 안 된다(요청 액션과 결과 상태는 개념적으로 다른 것이기 때문).

## 금액 등급 임계값 — `ApprovalService.amountGrade()` (182-188행)

| 조건 | 등급 | 실제 금액 기준(추정) |
|---|---|---|
| `a >= 10000000` | `"S"` | 1,000만원 이상 |
| `a >= 1000000` | `"A"` | 100만원 이상 |
| `a >= 100000` | `"B"` | 10만원 이상 |
| 그 외 | `"C"` | 10만원 미만 |

이 100만원 임계값(`1000000`)은 위 "지출(type=1) + 100만원 이상 → priority 자동 상향"(94행)의 기준값과 **숫자는 같지만 서로 다른 메서드(`processApproval` / `amountGrade`)에 각각 하드코딩**되어 있다 — 하나를 바꿔도 다른 하나는 그대로라 정책이 어긋날 위험이 있다.

## 참고 — enum 전환 시 유의점 (CLAUDE.md 불변 규칙)

이 문서의 모든 필드는 DB에 정수 그대로 저장돼야 하므로, enum화하더라도 `@Enumerated`가 아니라 `@Convert` + `AttributeConverter`로 코드값 매핑을 해야 한다. 특히 `Approval.status`의 `9`(취소)처럼 순번이 아닌 값이 저장 규칙에 포함된 경우 `@Enumerated(ORDINAL)`을 쓰면 즉시 어긋난다.
