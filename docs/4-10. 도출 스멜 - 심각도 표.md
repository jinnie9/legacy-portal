# 4-10. 도출 스멜 - 심각도 표

`4-4`~`4-9` 문서에서 개별적으로 조사한 내용을 종합해, 코드 스멜을 심각도순으로 정리한 문서.
`ApprovalService.java` 헤더 주석이 자체적으로 선언한 11개 스멜(God Class·Long Method·Magic Number·Duplicated Code·Tight Coupling·Feature Envy·Primitive Obsession·Long Parameter List·Poor Naming·Comment Smell·No Tests)을 전부 포함하며, 조사 과정에서 추가로 발견된 2건(DTO 부재, 구조적 비일관성)도 함께 담았다.

## 심각도 판단 기준

- **영향 범위**: 코드베이스에 얼마나 넓게 퍼져 있는가(도메인 1개 국한 vs 전체).
- **회귀 위험**: 이 스멜을 그대로 둔 채 다른 부분을 고치다 버그를 낼 가능성.
- **선행 필요성**: 다른 리팩토링보다 반드시 먼저 처리해야 하는가.

## 심각도 표

표 순서 = 심각도 내림차순(위에서 아래로 최상 → 하).

| 심각도 | 위치 | 스멜 | 권장 리팩토링 |
|---|---|---|---|
| 최상 | `src/test` (Java 테스트 클래스 0개) | **테스트 부재 (No Tests)** | 특성화 테스트 작성 — 현재 API 응답·DB 값·"조용한 무시" 동작까지 그대로 고정. 다른 모든 리팩토링에 선행. |
| 상 | `ApprovalService` 전체, 특히 `processApproval()`(86줄·중첩 깊이 6) | **God Class + Long Method** | 메서드 추출로 상신/승인/반려/취소를 `submit()`/`approve()`/`reject()`/`cancel()` private 메서드로 분리(공개 시그니처 `processApproval(id, userId, action, reason)`은 그대로 유지, 내부는 위임만). 상태 전이 규칙은 Rich Domain으로 `Approval` 엔티티로 이동. |
| 상 | `Approval`/`Notice`/`Schedule`/`User`의 `status`·`type`·`priority`·`category`·`role`, `action` 파라미터 | **Primitive Obsession / 매직넘버** | `@Convert` + `AttributeConverter`로 enum ↔ 기존 정수 매핑(DB 저장값 불변, `@Enumerated` 금지). `action`은 `Approval.status`와 별개인 `ApprovalAction` enum으로 분리(값이 우연히 같아도 개념은 다름). |
| 중상 | 감사로그·메일 발송·권한판정·null체크·본인확인 등 7개 패턴, 27곳 이상 | **중복 코드** | 공통 모듈 추출 — 감사로그·메일 발송 호출부를 공통 헬퍼로, `role >= 2` 권한판정은 `User.isManagerOrAbove()` 같은 도메인 메서드로 이동. |
| 중 | `SmtpMailSender`·`FileAuditLogger`, 5곳 | **강결합 (직접 `new`, DIP 위반)** | `MailSender`/`AuditLogger` 인터페이스 추출 + 생성자 주입. |
| 중 | `ApprovalService.amountGrade()`, 우선순위 자동 상향 로직 | **Feature Envy** | 금액 등급·우선순위 규칙을 `Approval` 엔티티 메서드로 이동(Rich Domain), 중복된 100만원 임계값을 상수 하나로 통합. |
| 중 | `ApprovalController`(`Map<String,Object>` 캐스팅), `ApprovalService.create()` 파라미터 8개 | **DTO 부재 + Long Parameter List** | 요청/응답을 record DTO로 분리(JSON 필드는 레거시와 동일 유지), `create()` 파라미터는 요청 DTO에서 그대로 위임받는 형태로 축소. |
| 하 | `d`/`u`/`s`/`proc`/`tmp`/`flag1`/`sc`/`n` 등, `ApprovalService`·`ScheduleService` 전반 | **Poor Naming** | 지역변수·파라미터명을 의미 있는 이름으로 교체(approval, user, status, action, label, isOverlapping, schedule, notice) — 인자도 예외 없이. |
| 하 | Poor Naming 발생 지점과 동일(나쁜 이름을 주석으로 변명) | **Comment Smell** | 별도 작업 불필요 — 이름을 고치면 자동 해소. "무엇"을 설명하는 주석은 삭제하고 "왜"만 남긴다. |

## 참고 — 심각도 평가에서 제외한 항목 (스멜이 아니거나 손대면 안 되는 것)

| 위치 | 항목 | 권장 조치 |
|---|---|---|
| `processApproval`/`publish`/`confirm` | 조용한 실패 (권한 없음·상태 불일치 시 예외 없이 무시) | **보존 대상** — 설계 결함처럼 보이지만 CLAUDE.md 기준 리팩토링 단계에서 절대 동작을 바꾸면 안 된다. 별도 재설계 단계의 논의 대상. |
| 4-4 참고 | 구조적 비일관성 (notice/schedule에 Controller 없음, user에 Service 없음) | **참고사항** — 스멜이라기보다 미완성 기능. 이번 리팩토링 범위와는 무관. |

## 순위별 근거 요약

1. **테스트 부재 — 최상**: 안전망이 전혀 없는 상태에서 2~9번 항목을 고치면 그 자체가 회귀 위험이다. 특성화 테스트 작성이 다른 모든 작업의 선행 조건.
2. **God Class + Long Method — 상**: 검증·영속화·메일·로그·권한판정·포맷팅이 한 클래스(특히 한 메서드)에 몰려 있어, 어느 하나를 건드려도 나머지 책임에 영향을 줄 위험이 가장 크다.
3. **Primitive Obsession/매직넘버 — 상**: 4번(중복된 권한판정)과 6번(Feature Envy의 임계값)의 근본 원인. 여기를 enum + `@Convert`로 정리하면 파생 스멜 여럿이 함께 옅어진다.
4. **중복 코드 — 중상**: 이미 `ScheduleService.confirm()`의 null-guard 누락처럼 복붙 과정에서 미세한 불일치가 실제로 발생했다 — 방치할수록 벌어질 문제.
5. **강결합 — 중**: 영향 범위(5곳)가 상대적으로 좁고 클래스 자체가 단순해, 인터페이스 추출 + 생성자 주입으로 비교적 기계적으로 해소 가능하다.
6. **Feature Envy — 중**: 도메인 규칙이 서비스에 있어 Rich Domain 전환 대상이지만, 지금 당장 버그를 유발하지는 않는다.
7. **DTO 부재/Long Parameter List — 중**: 오타·타입 오류가 컴파일이 아닌 런타임에 터지는 구조적 위험은 있으나, API 응답/요청 JSON 구조 자체는 이미 유효하게 동작 중이다.
8~9. **Poor Naming/Comment Smell — 하**: 가독성 문제이며 동작에 영향이 없어, 테스트만 갖춰지면 가장 안전하게 먼저 손댈 수 있는 항목이기도 하다.
