## 3. 핵심 Before/After 비교

### 3-1. God Class + Long Method → 오케스트레이션 + Rich Domain

**Before** (`512beb1`, `ApprovalService.processApproval()` — 약 75줄, 최대 중첩 6단계, if-else 체인):
```java

    Approval d = repo.findById(id).orElse(null);
    if (d == null) { return; }
    User u = userRepo.findById(userId).orElse(null);

    int s = d.getStatus();

        }
    } else if (proc == 2) {
        if (s == 1) {
            if (d.getApproverId() != null && d.getApproverId().equals(userId)) {
                if (u.getRole() >= 2) { /* 승인 처리... */ }
            }
        }
    } else if (proc == 3) { /* 반려 처리... */ }
    else if (proc == 9) { /* 취소 처리... */ }
```

**After** (`HEAD`, `ApprovalService.java:108-136` + `Approval.java:80-145`):
```java
// ApprovalService — 오케스트레이션만
public void processApproval(Long id, Long userId, int action, String reason) {
    Approval approval = repo.findById(id).orElse(null);
    if (approval == null) { return; }
    User actor = userRepo.findById(userId).orElse(null);
    if (actor == null) { return; }
    ApprovalAction requestedAction = ApprovalAction.fromCode(action);
    switch (requestedAction) {
        case SUBMIT -> submit(approval, userId);
        case APPROVE -> approve(approval, actor, userId);
        case REJECT -> reject(approval, actor, userId, reason);
        case CANCEL -> cancel(approval, userId);
        case null -> { /* 알 수 없는 action → 조용히 무시 */ }
    }
}

private void submit(Approval approval, Long userId) {
    if (!approval.submit()) { return; }   // 판단은 도메인이, 오케스트레이션은 서비스가
    repo.save(approval);
    /* 메일 발송 */
    audit.write("APPROVAL SUBMIT", approval.getId(), userId);
}

// Approval(도메인) — 판단은 여기서
public boolean approve(User actor, Long userId) {
    if (status != ApprovalStatus.SUBMITTED) return false;
    if (approverId == null || !approverId.equals(userId)) return false;
    if (!actor.isManagerOrAbove()) return false;
    status = ApprovalStatus.APPROVED;
    updatedAt = LocalDateTime.now();
    return true;
}
```
"위반 시 예외 대신 `false`로 조용히 무시"하는 레거시 동작은 그대로 보존(docs/4-22 상태 변경 흐름 참고).

## 6. 관찰 가능한 동작 불변 — 검증 내역

- **특성화 테스트**: `ApprovalServiceCharacterizationTest` 6개가 1차 전 구간(`7742d08`~`HEAD`)에서 **변경 없이 계속 green**(호출·기대값·DB값 동일). 최근 두 커밋(`9207b55`, `77346da`) 이후에도 재실행해 green 확인.
- **API 계약**: `/api/approvals`, `/api/approvals/{id}/process` 등 엔드포인트·`processApproval(id, userId, action, reason)` 시그니처 변경 없음.
- **DB 저장값**: `status`/`action` enum 전환에도 DB 컬럼은 여전히 정수(0/1/2/3/9, 1/2/3/9) — `AttributeConverter` 사용, `@Enumerated` 미사용.
- **조용한 무시 동작**: 권한 없는 승인 시도, 존재하지 않는 id, 알 수 없는 action 코드 — 전부 예외 없이 조용히 무시되는 레거시 동작을 그대로 보존(특성화 테스트 4·5·6번 + 실제 API 스모크 테스트로 재확인).
- **신규 단위 테스트**: `ApprovalServiceMailNotificationTest` 5개(`FakeMailSender`로 메일 발송 호출 검증) 추가 — 특성화 테스트와 별개 파일, 기존 테스트는 건드리지 않음.

## 8. 남은 과제 (2차 대상)

- **매직넘버 잔존**: `Approval.type/priority`, `Notice.status/category`, `Schedule.status`, `User.role` — 아직 `int`. `Priority`처럼 제너릭한 이름 대신 도메인 접두어(`ApprovalPriority` 등)를 붙일 것(사용자 피드백, 메모리 기록됨).
- **유사 중복 미해소**(docs/4-21 #2·3·4·7): 조회 후 null 가드 절(3곳), 메일 본문/제목 템플릿(4곳), 본인 확인 패턴 — 타입이 달라 완전한 코드 추출은 아니지만 템플릿화 여지가 있음.
- **우연 중복은 그대로 둘 것**(docs/4-21 #6·8): 상태 매직넘버 분기, 엔티티 생성 상용구 — 겉모습만 닮았을 뿐 도메인 규칙이 달라 억지로 합치면 안 됨.
- **`NoticeService`/`ScheduleService` 자체의 God Method**: `publish()`/`create()`가 여전히 검증+상태전이+메일+로그를 한 메서드에서 처리(Rich Domain 미적용) — `Approval`에 적용한 패턴을 `Notice`/`Schedule`에도 확장할 여지.
- **SonarQube 재분석**: `HEAD` 기준으로 재측정해 위 7절 표를 갱신.
- **Coverage 미측정**: JaCoCo가 Maven 빌드에 연동되지 않아 SonarQube가 커버리지 데이터를 못 받는 상태(REPORT_EFFECT 문서에 이미 기록된 한계, 미해결).

## 9. 결론

1차 리팩토링은 **"보이는 동작은 그대로, 안은 완전히 다시 짠다"**는 CLAUDE.md 원칙 아래 God Class/Long Method(가장 위험한 항목)까지 포함해 8개 백로그 항목 중 6개를 완료했다. 매 단계 특성화 테스트가 green으로 유지됐고, 최근 커밋들도 실제 API 스모크 테스트로 재확인했다. 남은 항목(#2·#3의 일부)은 이번 1차 범위에서 의도적으로 보류한 것으로, 2차 리팩토링의 시작점이 된다.
