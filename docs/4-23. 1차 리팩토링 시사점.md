# 4-23. 1차 리팩토링 시사점

`docs/REPORT_1차마무리_20260709.md`(전후 사실 기록)와 별개로, 이 문서는 **1차 리팩토링 과정에서 실제로 확인된 원칙·교훈**을 정리한다. "무엇을 바꿨는가"가 아니라 "그래서 무엇을 배웠는가"에 집중한다.

## 1. 순서가 결과를 결정했다

`docs/4-12` 백로그는 심각도(4-10/4-11) 순서가 아니라 **의존관계** 순서로 짰다 — 이름 개선(0위험) → enum 전환(중복·Feature Envy의 근본 원인 제거) → 중복 제거 → DI → God Class 분해(가장 위험) → DTO(마지막). 실제로 진행해보니:

- **이름을 먼저 고치니** 이후 모든 리뷰가 빨라졌다(약어 `d`/`s`/`proc`가 `approval`/`status`/`action`이 된 순간, if-지옥을 읽는 부담 자체가 줄었다).
- **enum을 먼저 넣으니** `role>=2` 같은 중복을 `User.isManagerOrAbove()`로 걷어낼 때 "이미 있는 도메인 개념을 재사용"하는 형태가 됐다 — enum 없이 중복부터 걷었다면 무엇을 기준으로 묶어야 할지 애매했을 것이다.
- **God Class 분해를 마지막 직전에 두니**, 정작 `processApproval()`을 쪼갤 때는 이름·enum·DI가 이미 끝난 상태라 "상태 전이 규칙을 어디로 옮길까"만 고민하면 됐다. 만약 이 분해를 0번째로 했다면 약어 변수명·매직넘버·강결합이 뒤섞인 채로 리팩토링해야 해서 훨씬 위험했을 것이다.

**시사점**: "제일 심각한 것부터"가 아니라 **"이걸 먼저 해야 다음이 안전해지는 것부터"**가 실전 순서다.

## 2. "관찰 가능한 동작 보존"은 원칙이 아니라 기법의 목록이다

CLAUDE.md의 "동작 변경 금지"는 선언만으로 지켜지지 않는다. 실제로 아래처럼 **구체적 기법 하나하나**로 구현됐다:

| 보존 대상 | 기법 |
|---|---|
| DB 저장값(정수) | `@Convert` + `AttributeConverter`(`@Enumerated` 금지 — ORDINAL은 `9`처럼 어긋나는 값과 안 맞음) |
| API 응답(정수) | enum에 `@JsonValue` — 없으면 Jackson이 기본값(이름 문자열)으로 직렬화해 응답 형식이 바뀜 |
| "조용한 무시" | 예외 대신 `boolean false` 반환(도메인) + guard clause의 조기 `return`(서비스) — 둘 다 "아무 일도 안 일어남"을 표현하는 같은 언어 |
| 알 수 없는 코드 | `ApprovalAction.fromCode()`는 `null` 반환(예외 아님) — 반면 `ApprovalStatus.fromCode()`는 예외를 던짐. **똑같아 보이는 fromCode 메서드가 왜 다르게 동작하는지**가 "이 값이 외부 입력인가, 내부에서만 도는 값인가"의 차이를 그대로 보여준다 |
| 원치 않는 JSON 노출 | `User.isManagerOrAbove()`에 `@JsonIgnore` — Jackson이 `isXxx()`를 bean getter로 오인해 필드를 자동 노출시키는 것을 막음(실제로 겪은 회귀, 아래 4번 참고) |

**시사점**: "동작을 보존한다"는 각 계층(DB/직렬화/도메인/서비스)마다 **다른 도구**를 요구한다. 하나의 기법으로 전부 해결되지 않는다.

## 3. Rich Domain 전환은 "God Class를 없앤다"가 아니라 "책임을 옮긴다"

`ApprovalService`는 여전히 `MailSender`/`AuditLogger`/`ApprovalRepository`/`UserRepository` 네 협력자를 조합하는 오케스트레이터다. God Class가 "사라진" 게 아니라 **"판단(무엇이 가능한가)"은 `Approval`로, "부수효과(무엇을 할까 — 저장·알림·기록)"는 서비스에 남았다.** `docs/4-19`(SRP 분석)가 8개 축 중 4개(A·B·F·H)만 빠져나가고 4개(C·D·E·G)가 남았다고 정리한 게 이 지점이다.

**시사점**: "God Class 해소"를 "메서드 하나 없애기"로 오해하면 안 된다. 실전에서는 **책임을 다른 축으로 재배치하는 것**이고, 남은 책임이 "성격이 균질한가"(예: 전부 "성공 후처리"라는 하나의 이유로 바뀐다)가 다음 리팩토링 여부를 가른다.

## 4. 회귀는 테스트가 아니라 실제 API 호출에서 잡혔다

`User.isManagerOrAbove()`를 추가했을 때 특성화 테스트는 계속 green이었지만, `/api/users`를 직접 호출해보니 `"managerOrAbove": true`가 JSON에 몰래 섞여 나왔다(Jackson의 `isXxx()` 자동 노출). 특성화 테스트는 `ApprovalService`만 검증했지 `UserController`의 응답 형식은 검증 범위 밖이었기 때문이다.

**시사점**: 특성화 테스트가 있어도 **테스트가 커버하지 않는 경계**는 여전히 육안 검증(smoke test)이 필요하다. "테스트가 green이니 안전하다"는 "테스트가 검증하는 범위 안에서만" 참이다.

## 5. 중복은 한 가지가 아니다 — 동일·유사·우연을 구분해야 손댈 곳이 보인다

`docs/4-21`에서 세 서비스의 중복을 분류해보니:

- **동일 중복**(감사 로그 조립, `role>=2`)은 "포맷을 바꾸면 다 같이 바뀌어야 하는" 진짜 중복이라 **Move Method로 즉시 해소**했다.
- **유사 중복**(조회 가드 절, 메일 템플릿, 본인 확인)은 구조는 같지만 타입·세부가 달라 **추출하려면 별도 추상화(제네릭/템플릿 메서드)가 필요**해서 1차 범위에서는 보류했다.
- **우연 중복**(상태 매직넘버 분기, 엔티티 생성 상용구)은 겉모습만 닮았을 뿐 **합치면 서로 다른 도메인 규칙이 뒤섞이는 실수**가 된다 — 이건 "제거해야 할 중복"이 아니라 "제거하면 안 되는 우연"이다.

**시사점**: "중복 코드"를 하나의 스멜로 뭉뚱그리면, 우연 중복까지 억지로 추출하다가 오히려 서로 무관한 두 정책을 하나로 묶는 새로운 결합을 만든다. **중복을 발견하면 바로 추출하지 말고, 먼저 "왜 닮았는가"(변경 이유가 하나인가, 우연인가)를 물어야 한다.**

## 6. 정량 지표는 방향은 보여주지만 전체 그림은 아니다

`docs/REPORT_EFFECT_20260708.md`에서 SonarQube Code Smells가 "37건 → 37건, 안 줄어든 것처럼" 보였지만, 실제로는 프로덕션 코드가 37→28건(-24%)로 줄고 테스트 파일의 한글 식별자가 Sonar 기본 네이밍 규칙과 충돌해 9건이 새로 잡힌 것뿐이었다. 반면 Cognitive Complexity(100→71, -29%)는 `processApproval()`의 중첩 평탄화를 정직하게 반영했다.

**시사점**: 정량 지표는 "무엇을 측정하는지"에 따라 리팩토링 효과를 가리기도(합계 지표), 정확히 보여주기도(구조적 복잡도 지표) 한다. **지표 하나만 보고 판단하지 말고, 왜 그 숫자가 나왔는지 파일 단위로 뜯어봐야** 진짜 효과와 착시를 구분할 수 있다.

## 7. 가장 저렴한 리팩토링이 가장 큰 지렛대였다

이름 개선(`d`→`approval`, `proc`→`action` 등)은 동작을 전혀 바꾸지 않는 가장 안전한 작업이었지만, 그 이후 모든 리뷰·리팩토링의 속도를 끌어올렸다. 반대로 God Class 분해(가장 위험도 높은 작업, `4-11` 점수 최고)는 그 안전한 사전 작업들이 끝난 뒤에야 상대적으로 안전해졌다.

**시사점**: 리팩토링 우선순위를 "효과 크기"로만 정하면 위험한 작업을 너무 일찍 만난다. **"위험 대비 지렛대"가 큰 것(이름·enum)을 먼저 처리해 다음 작업의 위험을 낮추는 것 자체가 전략**이다.

## 8. 의도적으로 안 건드린 것도 리팩토링의 결과다

- **조용한 실패**(권한 없음·상태 불일치 시 예외 없이 무시)는 명백한 설계 결함이지만 1차 범위에서 손대지 않았다 — 고치면 "리팩토링"이 아니라 "동작 변경"이기 때문이다(CLAUDE.md 보존 대상 vs 개선 대상 구분).
- **우연 중복**(상태 매직넘버, 엔티티 생성 상용구)도 의도적으로 그대로 뒀다 — 위 5번 참고.
- **`Notice.status`/`Schedule.status` 등 나머지 매직넘버**도 아직 int로 남겨뒀다 — `Approval`에서 검증된 패턴(AttributeConverter + Rich Domain)을 그대로 반복 적용할 수 있는 2차 대상으로 남겨둔 것이지, 놓친 게 아니다.

**시사점**: 리팩토링 보고서에서 "무엇을 바꿨는가"만큼 **"무엇을 왜 안 바꿨는가"**를 기록하는 게 중요하다 — 안 바꾼 이유가 명시되지 않으면, 다음 사람(또는 다음 세션의 나 자신)이 그걸 "놓친 버그"로 오해하고 성급하게 손댈 수 있다.

## 요약 — 다음 리팩토링에 가져갈 3가지 원칙

1. **의존관계 순서로 백로그를 짠다** — 심각도가 아니라 "이걸 먼저 하면 다음이 안전해지는가".
2. **중복을 추출하기 전에 "왜 닮았는가"를 묻는다** — 동일/유사/우연을 구분하지 않으면 우연을 억지로 합쳐 새 결합을 만든다.
3. **테스트가 검증하지 않는 경계는 직접 확인한다** — 특성화 테스트 green과 "실제로 안전함" 사이엔 항상 테스트 커버리지의 빈틈이 있다.
